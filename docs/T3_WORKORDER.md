## 2. T3-8 — sym16 절제 실험 (코드 수정 0)

### 왜 하는가

`src/v2/model/encoder.py` 는 *"비대칭 stride 가 이 설계의 핵심이다"* 라고 적고 있고,
이것이 논문 Method 의 **가장 독자적인 주장**이다. 그런데 근거가 **계산 논거뿐이다**:

> 눈꺼풀 상하 간격 8.73 px → 세로 stride 16 이면 **0.55 px** 가 되어 신호가 사라진다

**`grep -rl "sym16" results/` 결과 0건 — 한 번도 학습된 적이 없다.**
심사자가 반드시 묻는다: *"대칭 stride 를 실제로 돌려봤나?"*

| 구조 | 특징맵 | 세로 stride | 병목 눈꺼풀 | conv MMAC | PR-AUC |
|---|---|---:|---:|---:|---|
| sym16 | 128×4×10 | 16 | **0.55 px** | 9.22 | **미측정** |
| **vpres** (채택) | 64×32×5 | 2 | 4.37 px | **12.41** | 0.9886 ± 0.0038 |
| vfull | 64×64×5 | 1 | 8.73 px | 24.21 | 미측정 |

**vpres 는 sym16 보다 conv 연산이 34% 많다.** 그 비용을 정당화하는 숫자가 필요하다.

### 🔴 그런데 sym16 vs vpres 는 **교락된 비교다** (2026-08-05 발견)

`SPECS` 를 층별로 펼쳐 보면 두 구조는 **네 가지가 동시에 다르다.**

| | sym16 | vpres | vfull |
|---|---|---|---|
| **세로 stride** | 16 | **2** | 1 | ← 의도한 변수 |
| 가로 stride | 16 | **32** | 32 | ← 교락 |
| L1 커널 | (3,3) | **(3,5)** | (3,5) | ← 교락 |
| 채널 진행 | 16→32→64→**128** | 16→32→48→**64** | 16→32→48→64 | ← 교락 |
| flat_dim | 512 | **2048** | 4096 | ← 교락 |

**sym16 이 지더라도 "세로 해상도 때문"이라고 말할 수 없다.** 가로 stride·커널·채널·
flat_dim 이 전부 다르므로 "그냥 용량이 달라서"라는 반론이 그대로 성립한다.

반면 **`vpres` vs `vfull` 은 깨끗하다** — L2 의 세로 stride(2 vs 1) 하나만 다르고
커널·채널·가로 stride 가 전부 같다. 다만 이 둘은 **4.37 px vs 8.73 px** 로
**둘 다 신호가 살아 있는 구간**이라, "세로를 죽이면 망가지는가"라는 정작 궁금한 질문에
답하지 못한다.

### 해결 — 교락 없는 4번째 구조를 추가한다

`vpres` 에서 **세로 stride 만** 공격적으로 바꾼 것을 정의한다. 커널·채널·가로 stride 는 그대로.

```python
# src/v2/model/encoder.py  SPECS 에 추가
# vpres 와 커널·채널·가로 stride 가 전부 같고 세로 stride 만 16 이다.
# 세로 해상도 논거의 교락 없는 대조군.
"vdrop": [
    Conv(1, 16, (3, 5), (2, 4)), Conv(16, 32, (3, 3), (2, 2)),
    Conv(32, 48, (3, 3), (2, 2)), Conv(48, 64, (3, 3), (2, 2)),
],
```

→ 세로 stride 2×2×2×2 = **16** (눈꺼풀 **0.55 px**), 가로 4×2×2×2 = 32 (vpres 와 동일),
특징맵 64×4×5, flat_dim 256.

**`vpres` vs `vdrop` 이 논문에 실을 절제 실험이다.** 변수가 세로 stride 하나뿐이다.
`sym16` 은 "흔히 쓰는 대칭 설계"라는 **참조점**으로 함께 내되, 절제 주장의 근거로 쓰지 않는다.

> ⚠️ 이 4번째 구조를 추가할지는 **사람 승인 사항**이다 (§8). 추가하면 T3-8 이 6런 → 9런.

### 명령

```bash
# ① vpres 재현 기준선 — 같은 fold·seed 로 비교해야 공정하다
#    ⚠️ 확정 런(5fold×3seed)의 0.9886 과 직접 비교하지 마라. fold 수가 다르다
python -m src.v2.train_encoder --arch vpres --latent 16 \
    --folds 0 1 --seeds 0 1 2 \
    --out results/v2/abl_vpres_ref.json

# ② vdrop — 교락 없는 절제 대조군 (SPECS 에 추가한 뒤). ★ 논문에 실을 비교
python -m src.v2.train_encoder --arch vdrop --latent 16 \
    --folds 0 1 --seeds 0 1 2 \
    --out results/v2/abl_vdrop.json

# ③ sym16 — "흔히 쓰는 대칭 설계" 참조점. 절제 근거로는 쓰지 않는다
python -m src.v2.train_encoder --arch sym16 --latent 16 \
    --folds 0 1 --seeds 0 1 2 \
    --out results/v2/abl_sym16.json

# ④ vfull — 여유 되면 (비용 상한 확인용)
python -m src.v2.train_encoder --arch vfull --latent 16 \
    --folds 0 1 --seeds 0 1 2 \
    --out results/v2/abl_vfull.json
```

- `--save-models` **없음** ← 필수
- 점수 사이드카는 `results/v2/abl_*_scores/` 에 자동 저장된다

### 완료 조건

- 네 구조의 (PR-AUC ± , conv MMAC, 세로 stride, 병목 눈꺼풀 px, flat_dim) 표
- **주 판정**: `abl_vpres_ref` − `abl_vdrop` 의 짝지은 피험자 부트스트랩 95% CI
  ← **변수가 세로 stride 하나뿐인 유일한 비교다**
- 보조: sym16·vfull 은 참조점으로 병기하되 **교락을 명시**한다
- ⚠️ **vdrop 이 vpres 와 비슷하게 나오면 설계 주장을 바꿔야 한다.**
  그러면 세로 해상도 논거가 성립하지 않고, 더 싼 구조가 edge 에 유리하다.
  **결과를 보기 전에 이 가능성을 적어둔다**

### 예상 소요

## 3. T3-5 — embedding vector 차원 D 확정 (코드 수정 0)

### 왜 하는가

D=16 은 v1 스윕(8명·한쪽눈, **인용 금지**)에서 온 값이고, "작은 D 가 신원을 덜 흘린다"는

프라이버시가 범위 밖이 된 지금 **D 를 작게 유지할 근거가 남아 있지 않다.**

그리고 **D 를 키우는 비용이 거의 0이다** (`E.analyse()` 실측):

| D | conv MMAC | fc MMAC | 총 MMAC | fc 비중 |
|---:|---:|---:|---:|---:|
| 8 | 12.41 | 0.016 | 12.43 | 0.13% |
| **16** | 12.41 | 0.033 | **12.44** | 0.26% |
| 32 | 12.41 | 0.066 | 12.48 | 0.53% |
| 64 | 12.41 | 0.131 | 12.54 | 1.05% |

```bash
for D in 8 32 64; do

      --folds 0 1 --seeds 0 1 2 \
      --out results/v2/dim_D${D}.json
done
# D=16 은 T3-8 의 abl_vpres_ref.json 을 그대로 쓴다 (같은 fold·seed)
```

3. **성능 축의 실험은 여기서 멈춘다.** 더 돌려도 같은 답이 나온다.

### 재현성 — 덤으로 확인된 것

`abl_vpres_ref` 가 확정 런과 같은 (fold, seed) 를 3일 간격·커밋 2개 건너 다시 돌았는데
**6/6 이 비트 단위 동일**(차이 0.00e+00, best epoch 까지 일치). `repro.seal` 이 실제로 작동한다.

→ *"확정 런 0.9886 과 직접 비교하지 마라"* 는 **5-fold 집계에 대한 경고**이고,
**fold 0·1 개별값은 확정 런과 같은 숫자**다. 절제 비교에 그대로 쓸 수 있다.

### 비용 축 — `vdrop` 이 후보로 추가된다

| 구조 | conv MMAC | 인코더 params |
|---|---:|---:|
| **vdrop** | **3.44** | **50,752** |
| sym16 | 9.22 | 105,600 |
| vpres (현재) | 12.41 | 79,424 |

**`vdrop` 은 두 축 모두에서 가장 싸다** (vpres 대비 연산 **1/3.6**, 파라미터 64%).
sym16 처럼 축이 뒤집히지 않는다.

> ⚠️ **그래도 e2e 지연에서 큰 차이는 기대하기 어렵다.** v1 Pi 실측에서
> detect **7.76 ms** / infer **2.25 ms** / e2e p50 **11.53 ms** 였다 —
> **MediaPipe 얼굴 검출이 e2e 의 약 67%** 다. conv 를 72% 줄여도 e2e 는 최대 1~2 ms 준다.
> → **Table II 는 반드시 단계별 분해로 낸다.** 그리고 이 사실 자체가 논문에 쓸 결과다:
> *"에지 예산에서 지배적인 것은 표현 인코더가 아니라 얼굴 검출 프론트엔드다."*

## 3-quater. 🔒 Method 서술 사전 등록 (2026-08-05, **vdrop 결과를 보기 전에** 작성)

> **결과를 보고 서술을 고르는 것을 막기 위해 두 갈래를 미리 확정한다.**
> `PROTOCOL.md` §9-1 의 δ 확정, §14-5 의 G-R2 확정과 같은 방식이다.
> **결과를 본 뒤 이 절을 고치지 않는다.**

### 판정

`abl_vpres_ref` − `abl_vdrop` 의 PR-AUC 차이, 짝지은 피험자 부트스트랩 95% CI, δ = 0.02.

### 갈래 A — 차이가 없다 (CI 가 ±0.02 안에 들어온다)

**논문에 이렇게 쓴다:**

> 세로 해상도를 1/16 로 줄여 눈꺼풀 신호가 0.55 px 가 되어도 이 과제의 검출 성능은
> 유지되었다. 즉 **세로 해상도 보존은 이 데이터셋·이 과제 범위에서 성능을 좌우하지 않았다.**

- **설계 근거를 "성능"에서 "비용"으로 옮긴다.** Method 는 유도 논거 대신
  **인과적 스트리밍 구조**(§아래)를 중심에 놓는다
- **채택 구조는 `vpres` 를 유지한다.** 이유:
  - 확정 런·사이드카 점수·U1 분석·서브그룹 분석이 **전부 vpres 위에 있다.** 바꾸면 연쇄 재실행
  - v1 Pi 실측에서 e2e 가 예산의 **36%** 였다. **여유가 21 ms 이상이므로 3 MMAC 을
    아끼려고 구조를 바꾸는 것은 잘못된 최적화**다
  - sym16 은 MMAC 이 26% 적지만 **파라미터가 33% 많다**(105,600 vs 79,424).
    "더 싸다"가 축에 따라 뒤집힌다
- **단, Pi 실측에서 예산을 못 맞추면 그때 더 싼 구조로 간다.** 선택 기준은
  **MMAC 이 아니라 Pi 실측 e2e p99** 다
- 절제 표는 **그대로 싣는다.** 음성 결과도 결과다

### 갈래 B — 차이가 있다 (`vdrop` 이 δ 이상 낮다)

**논문에 이렇게 쓴다:**

> 눈꺼풀 간격 실측(8.73 px)에서 유도한 세로 해상도 제약이 실험으로 확인되었다.
> 세로 stride 를 16으로 두면 성능이 유의하게 떨어진다.

- 유도 논거를 Method 의 중심에 둔다. `vpres` 유지
- ⚠️ **그래도 "비대칭 stride 가 핵심"이라는 표현은 과하다.** 검증된 것은
  **세로 stride 하나**이고, 가로 32배 축소는 별도로 검증되지 않았다

### 어느 갈래든 공통 — Method 는 얇아지지 않는다

세로 논거가 빠져도 남는 것이 있고, 그중 하나는 **문헌 대비 실제로 차별적**이다.

| # | Method 요소 | 차별성 |
|---|---|---|
| 1 | **인과적 스트리밍**: 프레임당 인코딩 **1회** + 19프레임 링버퍼 | 🔴 **가장 강하다.** Nousias 2025 는 12프레임 **3D conv 블록**(35.4 M params). 프레임마다 19장을 다시 인코딩하면 비용이 19배가 되어 에지 예산을 넘는다. **이것이 에지를 가능하게 하는 설계 결정이다** |
| 2 | **양눈 크롭 정규화**: 회전 정렬 + 눈 사이 거리 × 2.2 → 고정 64×160 | 카메라 거리에 대해 스케일 정규화된다. 문헌은 48×48·50×50 **한쪽 눈** |
| 3 | **결측 마스크**: 얼굴 해소 실패 프레임을 pooling 에서 제외 | "변화 없음"과 "모름"을 구분한다 |
| 4 | **16차원 병목** | Nousias 2025 는 2048차원 |

> **요소 1을 Method 의 중심에 놓으면 세로 논거의 생사와 무관하게 Method 가 선다.**
> 그리고 그게 논문의 결론(에지 실시간)과 직결된다.

## 4. T3-1 — image_cnn 대조군 (코드 작성 필요) 🔴 논문의 핵심

### 🔴 2026-08-05 승인 보류 — 문헌 조사 후 결정

Claude Code 가 설계를 계산해 본 결과 **중대한 함정이 발견됐다.**

**함정**: `build_head` 의 TCN 이 `Conv1d(F,F,k=3)×3` 이라 비용이 **F²** 이다.
따라서 "병목 없음"(F=2048)은 시간 헤드만으로 ours 전체의 3배 연산 / 450배 파라미터가 되어
**구현 자체가 불가능**하다. 변형 B 는 실제로는 *"훨씬 넓은 병목(F≈256~512)"* 이지
"병목 없음"이 아니다. **논문에 "no bottleneck" 이라고 쓸 수 없다.**

**더 심각한 것**: F 를 줄이는 가장 싼 방법이 세로 해상도를 버리는 것이라,
MMAC ±10% 창에 드는 후보가 **둘 다 병목 눈꺼풀 0.55 px** 였다.

| 후보 | 백본 | F | 병목 px | 합계 MMAC |
|---|---|---:|---:|---:|
| B-a1 | sym16형 | 512 | **0.55** | 11.58 ✓ |
| B-c2 | vpres + 세로풀링8 | 256 | **0.55** | 13.00 ✓ |
| B-b1 | vpres형 C=16 (세로 보존) | 512 | 4.37 | 4.51 ✗ 예산 미달 |

즉 **예산 안에 드는 image_cnn 은 우리가 이긴다고 주장하는 바로 그 축에서 미리 불구가 된
베이스라인이다.** 이대로 돌려서 ours 가 이기면 PROTOCOL 부록 #8 —
*"결과가 유리하면 베이스라인이 불리해진 것은 아닌지 먼저 의심하라"* — 에 정확히 걸린다.
**심사자가 짚으면 방어할 수 없다.**

### 🔵 결정: 두 개는 **다른 비교**다. 분리한다

이 자리에서 섞여 있던 두 질문을 나눈다.

| | 질문 | 이름 | 무엇과 비교 |
|---|---|---|---|
| **(a)** | D차원 병목으로 압축하면 정확도를 잃는가 | **`abl_wide`** (절제) | **같은 백본**, 병목 폭만 16 vs 512 |
| **(b)** | 실제로 쓰이는 이미지 기반 방법과 견줄 만한가 | **`image_cnn`** (외부 베이스라인) | **문헌의 대표 구조** |

- **(a) 는 지금 결정할 수 있다.** Claude Code 제안대로 세로 stride 를 ours 와 **동일하게
  고정**하고 채널로만 예산을 맞춘다(B-b1 을 C=20~24). 변수가 **병목 폭 하나**로 좁혀져
  논문 주장과 정확히 일치하고, 베이스라인에 핸디캡을 주지 않는다.
  → **이름을 `matched` 가 아니라 `abl_wide` 로 한다.** "이미지 기반 베이스라인"이 아니라
  **절제 실험**이기 때문이다. 이름을 잘못 붙이면 논문에서 주장이 어긋난다.

- **(b) 는 지금 결정하면 안 된다.** 우리가 임의로 설계한 CNN 을 "이미지 기반 방법"이라고
  부르면 그게 바로 **허수아비(strawman)** 다. 전사문 03:02 가 요구한 것은
  *"이미지 기반으로 하는 애들과 성능 비교"* — **실제로 쓰이는 것**과 비교하라는 뜻이다.
  → **T6-1·T6-2 문헌 조사를 먼저 한다.** 공개 구현이 있으면 그것을, 없으면
  문헌에서 가장 흔한 구조를 근거와 함께 재현한다.

> 🔴 **T6(문헌 조사)가 T3-1(b)의 선행 작업으로 승격됐다.** 원래 P0 였지만
> "논문 쓸 때" 정도로 뒤에 있었다. 이제 **베이스라인 설계를 막고 있다.**

| 저자 결론 | latent 방식이 3D ResNet 에 **졌다** | — |

→ 주장을 *"encoder 를 쓴다"* 가 아니라
**"16차원 임베딩만으로 판정하고 에지에서 실시간으로 돈다"** 로 좁힌다.
새 연구 방향과 정확히 일치하므로 서사 손실은 없다.

### 할 일 (수정판)

1. **(a) `abl_wide`** — 세로 stride = ours 고정, 채널로 MMAC ±10% 맞춤.
   승인 완료. 큐가 비면 바로 돌린다
2. **(b) `image_cnn_mebal`** — 위 구조로 확정. **원문 확인 후** 착수.
   **문헌 근거(논문·구현 링크)를 결과 JSON 에 함께 기록한다**
3. `train_encoder.py` 에 `--front {ours,abl_wide,image_cnn}` 분기
   - ⚠️ 기존 `--arch`(인코더 구조: vpres/sym16/vdrop/vfull)와 **다른 축**이다. 혼동 금지

### 논문 서술 주의

- ❌ "no bottleneck" — 쓸 수 없다. F² 비용 때문에 구현 불가
- ✅ "a wider bottleneck (F=512 vs 16)" — 실제로 한 것
- ❌ 우리가 설계한 CNN 을 "the image-based baseline" 이라고 부르는 것
- ✅ 문헌 근거를 밝힌 재현 구조를 그렇게 부르는 것

### 왜 하는가

### 설계 — 기존 구조를 최대한 재사용한다

`src/v2/model/encoder.py` 는 이미 잘 분리돼 있다:

|---|---|
| `build(arch, d_latent)` | 크롭 → D차원 벡터 (**ours**) |

## 5-quinquies. ✅ T5-7 완료 + 데스크탑 실측 (2026-08-05 밤)

### 🔴 발견 1 — "인과적 TCN" 서술이 틀렸다. **논문 문구를 고쳐야 한다**

`encoder.py build_head` 는 *"인과적 TCN(dilation 1·2·4)"* 라고 적고 있으나
**실제로는 인과적이 아니다.** 대칭 패딩(`padding=dilation`)이라 창 안에서 미래를 본다.

**실측**: t=18 입력을 바꾸면 t=17 출력이 **4.72** 만큼 바뀐다 (t≤16 은 0).

| | 참/거짓 |
|---|---|
| TCN 이 인과적이다 | ❌ **거짓** — 창 안에서 양방향이다 |
| 시스템이 미래 프레임을 기다린다 | ❌ 거짓 — 프레임 t 의 판정은 **t−18..t 만** 쓴다 |
| **시스템 추가 지연이 0 이다** | ✅ **참** — 이것이 실제로 중요한 성질이다 |

**논문 문구**

- ❌ "causal TCN" / "인과적 시간 헤드"
- ✅ **"프레임당 1회 인코딩 + 19프레임 링버퍼 위의 양방향 TCN. 미래 프레임을 기다리지
  않으므로 시스템 추가 지연이 없다"**

> `src/v2/model/encoder.py` docstring 의 "인과적 스트리밍" 표현도 함께 정정할 것.
> 정확히는 **"미래를 기다리지 않는(non-lookahead) 스트리밍"** 이다.

### 🔴 발견 2 — "실시간" 주장에서 **두 지연을 구분해야 한다**

| 지연 | 값 | 뜻 |
|---|---|---|
| **처리 지연** (e2e) | **6.98 ms** (데스크탑 p50) | 프레임 1장을 처리하는 시간 |
| **검출 지연** (창 채움) | 학습이 **깜빡임 중심 창**을 썼으므로 창 끝에서 판정하면 최대 **~9프레임 ≈ 300 ms** | 깜빡임 발생 후 판정이 나올 때까지 |

### 🔴 확인 필요 — head 를 프레임당 몇 번 돌리나

- 비겹침이면 30 fps 에서 **633 ms 마다 한 번** 판정한다. 깜빡임은 100~400 ms 다 — **놓친다**

**권고: head 를 프레임마다 돌린다(stride 1). 비용은 0.0459 MMAC/frame 으로 보고한다.**
그래도 encoder 의 **0.37%** 라 무시할 수준이고, 배포 의미가 실제 깜빡임 검출과 맞는다.

> ⚠️ **0.0024/frame 으로 보고하면 실제로 배포하지 않을 구성의 숫자를 싣는 것이다.**
> `PROTOCOL.md` §12 대로 스트림 검출 성능은 평가하지 않지만, **지연은 실제 배포 구성으로 잰다.**

v1 은 **읽기만 하고 import 하지 않았다.** 프론트엔드는 `src/v2/dataset/crop.py` 에만 의존하며
기하·정규화를 직접 구현하지 않는다(위임이라 학습과 갈라질 수가 없고, G-Q2 가 그것을 검사).

**메시 공급자 분리**: `crop_from_mesh()` (메시를 인자로 받음 — 동치 검증용, MediaPipe 불필요) /
`process()` (MediaPipe — Pi 실행용). 이렇게 안 하면 동치 검증이 랜드마크 출처 차이까지 섞어 재게 된다.

### ⚠️ `refine_landmarks=False` 의 파급

v1 프론트엔드는 `refine_landmarks=True` 였다. 이번에 **False 로 바꿨다** — iris 랜드마크(468~477)는
크롭에 쓰이지 않는데 CPU 를 먹는다. 우리가 쓰는 눈꼬리 인덱스(33·133·160·144·158·153)는
전부 기본 468 메시 안에 있으므로 **안전하다.**

→ **detect 단계가 v1(7.76 ms)보다 빨라질 것이다.** 좋은 방향이지만
**v1 지연 수치와 나란히 놓을 근거가 하나 더 사라졌다.** (어차피 인용 금지)

### ⚠️ 이 숫자들은 아직 확정이 아니다

**vpres D=16 기준**이다. `vdrop`(3.44 MMAC, 50,752 params)이 차이 없게 나오면
최종 모델이 바뀔 수 있다. **Table II 는 구조 확정 후 다시 채운다.**

`src/v2/` 에는 **deploy 하위 디렉터리가 아예 없다.** T5-3·T5-7 이 v1 을 참고하라고
지시한 이유가 이것이다. **"v1 재사용 금지"는 결과·모델·수치에 대한 규칙이지 코드 학습이 아니다.**

### 🔴 지뢰 — 입력 정규화 불일치 (실측 확인)

```python
# v1: src/dataset/eye_preprocess.py  ← frontend.py 가 이걸 import 한다
def to_input_tensor(crop):
    x = np.asarray(crop, dtype=np.float32) / 255.0      # ← /255 만

# v2: src/v2/dataset/crop.py
INPUT_NORM = "frame_standardize"
    x = (x - x.mean()) / max(float(x.std()), EPS_STD * 255.0)   # ← 프레임 표준화
```

**v1 `frontend.py` 를 그대로 이식하면 `/255` 입력이 표준화로 학습된 v2 모델에 들어간다.**

> 🔴 **가장 위험한 형태로 실패한다.** 지연 시간은 입력 스케일과 무관하므로
> **벤치마크는 성공한 것처럼 보이고 판정만 조용히 망가진다.**
> Pi 측정 스크립트는 정확도를 검사하지 않는다.

### 이식 시 반드시 확인할 것

- [ ] **입력 정규화** — `src/v2/dataset/crop.to_input_tensor` 를 쓴다. v1 것을 import 하지 않는다
- [ ] **크롭 기하** — v1 `BOTH_MARGIN=2.2, OUT_H/W=64/160` 과 v2 `MARGIN=2.2, 64×160` 은
      **값은 같다.** 단 v2 는 `CropMeta`(interp_cubic·padded)와 mesh_xy 경로가 따로 있으므로
      **v2 `crop_both_eyes` 를 쓴다**
- [ ] **랜드마크 인덱스** — v1 `EAR_EYE_A` 와 v2 `EAR_EYE_A` 가 동일한지 대조
      (둘 다 `{"out":33,"in":133,"top1":160,"bot1":144,"top2":158,"bot2":153}` 로 보이나 확인)
- [ ] **동치 검증** — 같은 프레임에 v2 학습 경로와 Pi 프론트엔드를 각각 통과시켜
      **크롭·입력 텐서가 비트 단위로 같은지** 검사한다. 이 검사 없이 Pi 를 재지 않는다

## 9. 이번 라운드에서 **하지 않는** 구조 탐색

`SPECS` 의 세 구조는 **모델 동물원이 아니라 절제 축**이다. 스윕한 변수는
**세로 stride 하나뿐**이고, 다음은 **한 번도 탐색하지 않았다.**

| 미탐색 항목 | 현재 값 | 왜 안 하나 |
|---|---|---|
| 층 수 | 4층 고정 | 논문 기여가 구조 탐색이 아니다 |
| 채널 폭 | 16→32→48→64 고정 | 위와 동일 |
| residual / BN 변형 / attention | 없음 | 4페이지에 들어갈 자리가 없다 |
| 커널 크기 | 3×3 (L1 만 3×5) | 위와 동일 |
| pooling 방식 | 가로 평균 pooling 고정 | 위와 동일 |
| 입력 크기 | 64×160 🔒 | PROTOCOL §8-bis 확정 |

**이것은 약점이 아니라 선택이다.** 이 구조는 아키텍처 탐색이 아니라
**실측 물리량(눈꺼풀 8.73 px)에서 유도**됐다. 논문에서는 그렇게 서술한다 —
*"우리는 50개 구조를 시도해 이걸 골랐다"* 보다 *"측정된 제약에서 이 설계가 따라온다"* 가
4페이지 포맷에 맞고 방어하기도 쉽다.

> ⚠️ **단, 그 서술이 성립하려면 §2 의 절제 실험이 반드시 있어야 한다.**
> 유도 논거를 내세우면서 그 논거를 검증하지 않으면 그게 진짜 약점이 된다.

심사자가 "더 나은 구조가 있을 수 있다"고 물으면 **Limitations 에서 인정한다.**
구조 최적화는 후속 연구다.
