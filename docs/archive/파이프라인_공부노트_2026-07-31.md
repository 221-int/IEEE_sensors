# 0. 한 장 요약

**만드는 것**: 눈 영상을 저장하지 않고 **128차원 벡터**만으로 깜빡임을 검출하는

**핵심 주장**: 프라이버시가 정책·약속이 아니라 **구조**에서 나온다. 저장·전송되는 것은
벡터뿐이고 디코더를 배포하지 않으므로 원본으로 되돌릴 수단 자체가 없다.

**현재 정직한 위치** (2026-07-30 정정 반영):

| 축 | 상태 |
|---|---|
| 엣지 | ✅ **확정.** Pi5 e2e p99 12.06 ms = 30 fps 예산의 36%. 논쟁 여지 없는 유일한 결과 |
| 유용성 | ⚠️ **판정 불가 → 열세 가능성.** 조밀 격자로 재면 Ours 0.803±0.321 vs EAR 0.977±0.035 |
| 프라이버시 | ❌ **문제 확인 단계.** 벡터에서 선형 프로브 재식별 99.4%. 차원 축소는 방어가 아님 |

**그래서 mEBAL2(58명)를 붙이는 이유**: 8명으로는 위 ⚠️와 ❌ 둘 다 해석이 안 된다.
신원이 8개뿐이면 "재식별 99%"도 "EAR과 대등"도 표본이 너무 작아 주장이 되지 않는다.

# 1. 왜 이 문제인가 (문제 정의)

눈을 계속 촬영하는 기기는 기능이 정상 동작해도 사용자가 거부감을 느낀다. 눈 영상은
생체정보이고, 촬영된 영상이 어디에 남는지 알 수 없기 때문이다.

기존 방식은 이렇다.

```
카메라 → 원본 프레임 → MediaPipe 랜드마크 → EAR 계산 → 임계값 비교 → 깜빡임 O/X
                        ↑ 여기서 원본 픽셀이 그대로 존재하고, 저장하면 그대로 남는다
```

**EAR**(Eye Aspect Ratio)은 눈꺼풀 위아래 거리 ÷ 눈 가로 길이다. 눈을 감으면 분자가
작아지므로 값이 떨어진다. 단순하고 빠르고 학습이 필요 없다 — 그래서 20년 가까이
표준 베이스라인이다. **우리가 이겨야 하는 상대이자, 우리가 대체하려는 규칙이다.**

우리가 바꾼 질문: **"눈 영상을 보존하지 않고도 눈 상태를 다룰 수 있는가?"**

```
카메라 → 원본 프레임 → 양눈 크롭 → [인코더] → 128차원 벡터 → [MLP] → 깜빡임 O/X
                                              ↑ 저장·전송되는 건 여기부터. 원본은 즉시 버린다
```

> ⚠️ **프라이버시 주장의 정확한 범위.** 이 프라이버시는 **배포된 제품(Pi5)의 성질**이지
> 연구 파이프라인의 성질이 아니다. 학습 데이터를 만들려면 당연히 원본을 쓴다.
> 주장은 "배포된 시스템이 원본을 저장하지 않는다"이지 "연구자가 원본을 안 만진다"가 아니다.
> 이 구분을 흐리면 발표에서 바로 무너진다.

## 성공의 세 축

1. **유용성** — 깜빡임 검출이 EAR 규칙 베이스라인과 동급 이상이어야 한다.
   못 이기면 "굳이 학습 모델을 쓸 이유"가 없어진다.
2. **프라이버시** — 벡터에서 원본을 복원할 수 없고, **신원을 알아낼 수 없어야** 한다.
3. **엣지** — Pi5에서 실시간(30 fps = 프레임당 33.3 ms 이내).

세 축은 서로 당긴다. 유용성을 올리려고 벡터를 키우면 신원이 더 새고, 프라이버시를
위해 정보를 지우면 유용성이 떨어지고, 둘 다 올리려고 모델을 키우면 엣지 예산을 넘는다.
**이 트레이드오프를 정량화하는 것이 논문의 본체다.**

# 2. 파이프라인 전체 구조

## 2.1 큰 그림 — 네 갈래

같은 전처리를 공유하는 네 경로가 있다. **이 공유가 이 프로젝트의 설계 핵심이다.**

```
                     ┌──────────────────────────────────────┐
   [A] 데이터 생성    │  원본 영상 + 라벨                     │
                     │      ↓ 눈꼬리 4점                     │
                     │  ★ eye_preprocess.crop_both_eyes ★   │  ← 단일 진리원
                     │      ↓ 64×160 grayscale uint8         │
                     │  .npz (images, subject, frame_id, …)  │
                     └───────────────┬──────────────────────┘
                                     │
              ┌──────────────────────┼───────────────────────┐
              ↓                      ↓                       ↓
   [B] 학습              [C] 평가·실험            [D] 배포(serve)
   autoencoder →          eval_events              카메라 프레임
   encoder.pt             split_eval                   ↓
        ↓                 identity_probe          MediaPipe FaceMesh
   classifier.pt          recon_attack                 ↓ 눈꼬리 4점
        ↓                 dim_sweep               ★ 같은 crop 함수 ★
   train_disentangled     ear_baseline                 ↓
                                                  ONNX encoder → MLP
```

## 2.2 왜 "단일 진리원"에 집착하는가

**학습 때와 추론 때 크롭 기하가 1픽셀이라도 다르면 모델이 조용히 망가진다.** 정확도가
0이 되는 게 아니라 조금 떨어지고, 원인을 찾기가 극히 어렵다.

그래서 `src/dataset/eye_preprocess.py` 하나에 크롭 기하를 전부 몰아넣고, **데이터 생성
경로와 추론 경로가 같은 함수를 호출**하도록 강제한다. 두 경로가 다른 것은 **눈꼬리 4점을
어디서 얻느냐**뿐이다.

| 경로 | 눈꼬리 출처 |
|---|---|
| Eyeblink8 데이터 생성 | `.tag` 파일의 수동 주석 |
| mEBAL2 데이터 생성 | 배포된 `landmarks.csv`(FaceMesh 468점, 픽셀) |
| 배포(Pi) | MediaPipe FaceMesh 실시간 검출 |

이 원칙 덕분에 mEBAL2를 붙일 때 **크롭 코드를 새로 짜지 않았다.** 좌표계 인자
(`coords={'norm','pixel'}`) 하나만 추가하면 됐다.

> 같은 상수/로직이 두 파일에 복사되면 반드시 갈라진다. 이 프로젝트에서 실제로 **세 번**
> 사고가 났다(임계값 격자 3종, `set_seed` 3벌, EAR 인덱스 2벌). 2026-07-31에 EAR 인덱스는
> `eye_preprocess.EAR_EYE_A/B`로 통합했고, 격자·시드는 아직 남아 있다(Phase −1).

# 3. 단계별 상세

## 3.1 전처리 — `src/dataset/eye_preprocess.py`

**계약**: 눈꼬리 4점(픽셀) → `64×160` grayscale uint8 한 장.

```python
crop_both_eyes_from_corners(frame_bgr, le_a, le_b, re_a, re_b) -> (64, 160) uint8
```

내부 순서:

1. **양눈 중심 계산** — 왼눈 두 꼭짓점의 중점, 오른눈 두 꼭짓점의 중점.
2. **span** = 두 눈 중심 사이 거리. 얼굴 크기의 대리 척도다.
3. **crop_w = span × BOTH_MARGIN(2.2)**, `crop_h = crop_w × 64/160`.
   → **얼굴이 크든 작든 눈 주변을 같은 비율로 담는다**(스케일 정규화).
4. **회전 정렬** — 두 눈 중심을 잇는 선이 수평이 되도록 회전. 고개를 기울여도 같은 그림이
   되게 한다. 각도는 ±90° 안으로 정규화해 180° 뒤집힘을 막는다.
5. **grayscale → 64×160 리사이즈.** 축소면 `INTER_AREA`, 확대면 `INTER_CUBIC`.

파라미터의 의미:

| 상수 | 값 | 왜 |
|---|---|---|
| `OUT_H, OUT_W` | 64, 160 | 양눈이 들어가는 최소한의 가로 비율. 한쪽 눈 64×64에서 넘어옴 |
| `BOTH_MARGIN` | 2.2 | 눈 사이 거리의 2.2배 → 눈꼬리 바깥 여유까지 포함 |
| `ALIGN_ROTATION` | True | 머리 기울기 제거 |
| `GRAYSCALE` | True | 색은 깜빡임에 무관, 채널 1/3 → 연산·용량 절감 |

**속도 최적화 (ROI warp)**: 크롭 박스가 프레임 안에 완전히 들어가면 전체 프레임을
회전시키지 않고 **박스만 워프**한다. 대상 픽셀이 ~60배 적어 Pi에서 크롭이 7.8배 빨라졌다.
대신 OpenCV 고정소수점 반올림 위치가 달라져 **비트 단위로 동일하지 않다**(2,400 프레임에서
평균 0.0042/255, 최대 5). 참고로 MediaPipe와 수동 주석의 크롭 차이는 MAE 6.7/255로 약
1,600배 크다. 즉 최적화 오차는 이미 존재하는 오차에 묻힌다.

**입력 텐서화**:

```python
to_input_tensor(crop)  # (1,1,H,W) float32, 그냥 /255. 평균·표준편차 정규화 없음
```

평균·표준편차 정규화를 **일부러 안 한다.** Pi 배포 경로와 학습 경로를 바이트 단위로
맞추기 위해서다. 대신 이 때문에 데이터셋 간 밝기 차이가 그대로 모델에 들어간다
(§5의 mEBAL2 34.8 vs Eyeblink8 102.7). 이건 알고 있는 트레이드오프다.

## 3.2 데이터셋 생성 — `.npz` 한 덩어리

```
images      uint8  [N, 64, 160]   크롭
subject     str    [N]            'eb01' / 'm01' — 피험자 분리 분할의 키
frame_id    int32  [N]            원본 프레임 번호
blink_id    int32  [N]            같은 깜빡임 이벤트에 속한 프레임끼리 같은 값, 아니면 -1
blink_event uint8  [N]            blink_id != -1
eye_closed  uint8  [N]            완전 폐안 여부 (Eyeblink8 .tag의 RE_FC == 'C')
```

**왜 npz 한 덩어리인가**: 학습·평가 스크립트가 전부 이 파일 하나만 읽으면 되고, 크롭
기하가 바뀌면 이 파일을 다시 만드는 것으로 전 경로가 동기화된다. 그래서 **전처리를 바꾸면
npz 재생성 → 재학습 → ONNX 재export → Pi 재벤치가 연쇄된다**(이게 밝기 정규화 도입을
보류한 이유다, §6.2).

**`blink_id` 가 중요한 이유**: 평가 단위가 프레임이 아니라 **이벤트**이기 때문이다(§3.5).

## 3.3 인코더 — `src/encoder/train_autoencoder.py`

**오토인코더**를 비지도로 학습하고 **인코더만 배포**한다.

```
Encoder:  1×64×160
  → Conv(1→32,  s2) BN ReLU     32×32×80
  → Conv(32→64, s2) BN ReLU     64×16×40
  → Conv(64→128,s2) BN ReLU    128× 8×20
  → Conv(128→256,s2)BN ReLU    256× 4×10
  → flatten(10240) → Linear → z (128차원)

Decoder:  z → Linear → 256×4×10 → ConvTranspose ×4 → 1×64×160   (로컬 검증 전용, 미배포)
```

- **왜 오토인코더인가**: 깜빡임 라벨은 비싸고 적다. 라벨 없이 "눈을 재현할 수 있는
  벡터"를 먼저 만들고, 그 위에 작은 판정기를 얹는 구조다.
- **왜 디코더를 안 배포하는가**: 배포하면 벡터→이미지 복원 도구를 같이 주는 셈이다.
  미배포가 곧 프라이버시 장벽이다. 다만 **"장벽"이지 "불가능"이 아니다**(§3.7).
- **분할**: 피험자 분리(clip 단위 홀드아웃). 외운 사람으로 평가하지 않기 위해서.

**잠재 차원 128의 근거는 실험으로 기각됐다.** 32~512 스윕 결과 32차원으로도 유용성이
충분했고(→ 128은 병목이 아니었다), **512→32로 16배 좁혀도 선형 재식별이 99%+ 유지**됐다.
즉 **차원 축소는 프라이버시 메커니즘이 아니다.** 이게 disentanglement로 간 이유다.

## 3.4 판정기 — `src/classifier/train_classifier.py`

```
z (128) → Linear(128→64) ReLU Dropout(0.3) → Linear(64→1) → sigmoid → blink 확률
```

인코더는 **얼려서**(frozen) 쓴다. 즉 벡터가 깜빡임을 이미 분리해 담고 있는지를 직접
시험하는 구조다. 클래스 불균형(깜빡임 프레임이 훨씬 적음)은 BCE `pos_weight`로 처리한다.

이 MLP가 하는 일은 **EAR 임계값 규칙의 학습된 대체물**이다. 그래서 비교 대상이
"EAR + 고정 임계값"인 것이다.

## 3.5 평가 — 왜 프레임이 아니라 이벤트인가

`src/eval/eval_events.py`

- **이벤트 recall** = 검출된 깜빡임 / 전체 깜빡임. 한 이벤트의 **프레임 중 하나라도**
  양성이면 검출로 친다. → 사람이 체감하는 "깜빡임을 놓쳤나"에 대응한다.
- **프레임 false-alarm** = 깜빡임이 아닌 프레임에서 양성이 뜬 비율. precision 대리 지표.

깜빡임은 0.1~0.4초(3~12프레임)라 프레임 단위 정확도는 "안 깜빡임" 클래스가 압도해
의미가 없다. 그래서 **recall이 1순위 지표**이고 false-alarm은 예산(3%) 안에 두는 제약이다.

### 임계값 격자 함정 (실제로 겪음)

예전엔 임계값을 0.3~0.8의 성긴 격자로만 훑었다. 그러면 **저 false-alarm 구간을 아예
보지 못해** 비교가 왜곡된다. 지금은 조밀 격자(0.02~0.98, 97점)가 기본이다.
**중요한 건 ours와 baseline에 똑같은 격자를 주는 것**이다. 다르면 그건 방법 비교가 아니라
격자 비교다. (현재 코드베이스에 격자 정의가 3벌 남아 있다 → Phase −1)

## 3.6 정식 평가 프로토콜 — `src/experiments/split_eval.py`

**고친 문제**: 에폭과 임계값을 val 2명에서 고르고 **그 val 2명에서 보고**하고 있었다.
시험 문제를 보고 공부한 뒤 그 시험을 치는 것과 같다. 40에폭 × 97임계값 중 최고를 고르면,
재려던 효과만큼이 그대로 부풀려진다.

**프로토콜**: 8명에 대한 피험자 단위 **4-fold 회전**.

| 역할 | 인원 | 하는 일 |
|---|---|---|
| train | 4명 | 가중치 학습 |
| val | 2명 | **에폭·임계값 선택** |
| test | 2명 | **보고만.** 이 시점까지 한 번도 안 봄 |

모든 피험자가 test 1회 · val 1회 → **408 이벤트 전부가 test로 쓰인다**(기존 74개).
임계값은 val에서 "false-alarm 예산 안에 드는 가장 낮은 값"으로 고른 뒤 **얼려서** test에
적용한다. **EAR도 완전히 동일한 절차**를 거친다 — 그래야 프로토콜이 맞춰진 비교다.

**측정된 낙관 편향 = +0.085** (val 0.938 → test 0.854). 이 숫자 자체가 보고 가치가 있다.

### 임계값 보정 (새 발견)

절대 확률 임계값이 사람을 넘어가지 못한다는 게 드러났다. 사람마다 눈 모양·조명이 달라
같은 0.5가 다른 의미가 된다. 네 가지를 비교했다.

| 보정 | 뜻 |
|---|---|
| `none` | 절대 임계값 그대로 |
| `rank` | 그 사람 점수 분포 안에서의 **분위 순위**로 판정 → 사람별 자동 적응 |
| `zscore` | 그 사람 평균·표준편차로 표준화 |
| `rolling` | 최근 N프레임 이동 통계로 표준화 |

`rank`가 크게 이겼다(recall 표준편차 0.321 → 0.042). 반면 `zscore`/`rolling`은 **오히려
나빠졌고 원인이 아직 규명되지 않았다.** 미해결 항목이다.

## 3.7 프라이버시 실험 두 갈래

프라이버시를 "복원"과 "신원" 두 축으로 나눠 재는 것이 이 프로젝트의 관점이다.

### (a) 복원 공격 — `recon_attack.py`

**위협 모델**: 공격자는 벡터를 갖고 있다(그게 시스템이 내보내는 전부니까). 우리 디코더는
없지만 **배포된 인코더에 자기 이미지를 넣어 (이미지, 벡터) 쌍을 만들 수 있다.**
따라서 **디코더를 새로 학습할 수 있다.** 미배포는 장애물이지 불가능성이 아니다.

**대조군이 핵심이다.** 눈 크롭은 저분산 그레이스케일이라 아무 정보 없이도 PSNR이 높게
나온다. 그래서 넷을 같이 본다.

| 조건 | 뜻 | 실측 |
|---|---|---:|
| `ours` | 우리 디코더 (상한) | 33.79 dB |
| `attacker` | 공격자가 새로 학습한 디코더 | **23.13 dB** |
| `mean` | 학습셋 평균 이미지를 그냥 출력 (**정보 0의 하한**) | 17.26 dB |
| `shuffled` | 짝이 안 맞는 벡터 투입 (디코더가 벡터를 진짜 읽는지 검증) | 20.02 dB |

해석: 총이득 +5.87 dB 중 "일반적 눈 형태" +2.76, **벡터 고유 정보 +3.11**. 디코더 미배포
장벽은 10.65 dB. 육안 식별은 불가. → **"복원 불가"가 아니라 "복원 곤란"** 으로 표현을 낮췄다.

### (b) 신원 프로브 — `identity_probe.py`

**예상 질문**: "EAR은 스칼라 하나라 신원이 없을 텐데, 그럼 EAR이 더 안전한 것 아닌가?"

공정하게 재려면 **내보내는 숫자 개수를 맞춰야 한다.** 우리는 프레임당 128개, EAR은 1개다.
그대로 비교하면 우리가 더 새는 게 당연하다.

| 조건 | ours | 비교 대상 |
|---|---|---|
| [A] 시스템이 실제 내보내는 것 | 벡터 128 | EAR 스칼라 1 |
| **[B] 숫자 개수를 맞춤 (핵심)** | 벡터 128 | **EAR 연속 128프레임** = 숫자 128개 |
| [C] 현실적 저장물 | 벡터 | EAR 창의 요약통계 |

[B]가 중요한 이유: **깜빡임 동역학(빈도·지속시간·파형)은 그 자체로 생체 신호다.**
스칼라라서 안전한 게 아니라, 시간축을 주면 스칼라도 샌다. 이걸 재지 않으면 "EAR이 더
안전하다"에 반박할 근거가 없다.

모든 표현에 **동일한 선형 프로브 + 동일한 분할**을 쓴다(공격자 과제 = 같은 피험자,
다른 프레임). 프로브 용량이 다르면 비교가 오염된다. 창은 겹치지 않게 자른다.

실측: 선형 프로브 재식별 **ours 0.994 vs EAR 0.170** — 프라이버시 병목은 복원이 아니라
**신원**이라는 게 여기서 나왔다.

### (c) disentanglement — `train_disentangled.py`

신원을 **표현 자체에서** 제거하려는 시도. 인코더에 두 머리를 단다.

```
        ┌→ blink head    (128→64→1)        : 깜빡임을 맞춰라        (BCE 최소화)
z(128) ─┤
        └→ identity head (128→128→n_subj)  : 누구인지 맞춰라
             ↑ GRADIENT REVERSAL (×−λ)
```

**GRL(gradient reversal layer)** 은 순전파에서는 아무것도 안 하고 **역전파에서 그래디언트
부호를 뒤집는다.** 그 결과 identity head는 신원을 맞추려고 학습하는데, 인코더는 그 head가
**틀리도록** 밀린다. 즉 "깜빡임은 남기고 신원은 지워라"가 하나의 목적함수가 된다.

λ가 그 세기다. λ 스윕으로 **파레토 곡선**을 그린다.

```
  y: 유용성 (깜빡임 AUC / 분류 정확도)
  │   ●λ=0            ← 신원 다 샘, 유용성 최고
  │      ●λ=0.1
  │          ●λ=1     ← 우리가 원하는 구간: 유용성 유지 + 신원만 하강
  │              ●λ=3 ← 과하면 유용성도 무너짐
  └──────────────────→ x: 재식별 정확도 (낮을수록 좋음)
```

**"유용성을 유지하면서 신원만 떨어지는 구간이 존재하는가"** — 이게 이 프로젝트에
남은 유일한 정당화 근거다. 존재하지 않으면 주장이 성립하지 않는다.

> ⚠️ 기존 λ 스윕 결과(재식별 0.94→0.77)는 **한쪽 눈 64×64 시절 예비 결과**이고
> 양눈 인코더로 재실행하지 않았다. **인용 금지.**

## 3.8 배포 — `src/deploy/`

```
frontend.py    카메라 프레임 → MediaPipe FaceMesh → 눈꼬리 4점 → 같은 크롭 → (1,1,64,160)
export_onnx.py encoder.pt + classifier.pt → ONNX
run_video.py   Pi에서 단계별 지연 측정 (--mode ours | ear)
```

# 6. 새 파이프라인 설계 (Phase 0 → 4)

## Phase 0 — 로더·어댑터 ✅ 완료

**새로 만든 것**

```
src/dataset/mebal2_loader.py     mEBAL2 CSV → 얼굴 해소 → 눈꼬리 4점 → 기존 크롭 호출
src/tools/check_mebal2.py        User 1 §7 재현 회귀 테스트
```

**기존 코드 수정**

```
eye_preprocess.py   coords={'norm','pixel'} 인자 추가 (기본 norm → 기존 경로 불변)
                    EAR 인덱스 상수를 여기로 승격 (ear_baseline이 import)
```

### 설계 판단 네 가지

**(1) 좌표계는 인자로, 기본값은 기존 동작.**
mEBAL2 랜드마크는 픽셀인데 `_landmark_xy`는 정규화를 가정해 `w, h`를 곱한다. 그대로 쓰면
좌표가 1000배 부풀려진다. 기본값을 `norm`으로 둬 **MediaPipe/Pi 경로가 바이트 단위로
불변**임을 검증했다(정규화 입력과 픽셀 입력이 동일 크롭 산출).

**(2) box 개수와 landmark 개수는 `assert`가 아니라 기하 매칭.**
원래 계획은 "프레임마다 box 개수와 일치 assert"였는데, **실제로는 6.0% 프레임에서
불일치**한다.

| landmark 얼굴 | box 얼굴 | 프레임 | 뜻 |
|---:|---:|---:|---|
| 0 | 0 | 1,147 | 얼굴 자체를 못 찾음 |
| **0** | **1** | **2,154** | 박스는 있는데 메시 실패 |
| 1 | 1 | 32,801 | 정상 |
| **1** | **2** | **104** | 박스 2개, 메시 1개 → **인덱스 매칭 불가** |
| 2 | 2 | 1,435 | 정상 |

그래서 **메시 중심점이 어느 박스 안에 들어가는지**로 매칭한다. 2얼굴 프레임 200개(400건)에서
100% 자기 박스에 들어가는 것을 확인했다.

**(3) 얼굴 선택 규칙을 고정.** 메시가 있는 얼굴 중 **박스 면적 최대**. 박스가 없으면 메시
자체의 바운딩 박스 면적으로 대체. **규칙이 프레임마다 흔들리면 크롭이 튄다.**

**(4) 영상 시킹 금지.** `CAP_PROP_POS_FRAMES`는 h264에서 가장 가까운 키프레임으로 가고
**조용히 엉뚱한 프레임을 돌려준다** → 크롭이 전부 어긋난다. 순차 `grab()/retrieve()`만 쓴다.
(측정 584 fps이므로 20,000 프레임 건너뛰기가 34초.)

## Phase 1 — 크롭 기하 게이트 ⬜

**게이트다. 통과 못 하면 여기서 멈춘다.** 58명을 돌리기 전에 "우리 전처리가 mEBAL2에서
Eyeblink8과 같은 분포의 그림을 만드는가"를 확인한다.

- 대상: `span`, `crop_w/crop_h`, 정렬 각도, 선명도(라플라시안 분산), 리사이즈 방향
- **제외: 밝기** (결정 2로 정규화를 안 하므로 애초에 맞출 대상이 아님)
- 허용 기준선: `.tag` 수동 크롭 vs MediaPipe 크롭의 차이 **MAE 6.7/255**. 이 안이면 "같은 분포"
- 실패 시: **58명 전체를 돌리지 말 것.** 대안은 제공 랜드마크 대신 MediaPipe 직접 재실행
  (serve 경로와 완전히 같아지지만 전 프레임 디코딩 비용 발생)

> **왜 제공된 눈 크롭을 안 쓰는가** ① 눈을 따로 자른 이미지에서는 `BOTH_MARGIN × 눈중심간거리`
> 스케일 규칙을 복원할 수 없다 ② 우리는 양눈 중심선으로 회전 정렬하는데 눈별 크롭은 기준이 다르다
> ③ Pi serve 경로가 단일 크롭 함수라 train/serve 기하가 갈라진다 ④ 크기가 제각각(64/44/54)

## Phase 2 — 대량 전처리 ⬜

**압축을 풀지 않는다.** 전부 풀면 477 GB지만 한 번에 필요한 건 8 GB 남짓이다. zip은 중앙
디렉터리로 개별 엔트리 랜덤 액세스가 되므로 110 GB 아카이브에서 특정 사용자 파일만 꺼낼 수 있다.

```
for User N in 1..58:
    zip에서 User N 의 color.mp4 + landmarks.csv + box.csv 만 추출     (≈8 GB)
    라벨된 이벤트 프레임만 디코딩 → 양눈 크롭 → npz 에 append
    추출본 삭제
```

**피크 디스크 ≈ 8 GB**, 최종 산출물 `data/processed/mebal2_eyes.npz` (약 5.6 GB).
원본 zip 441 GB는 **크롭 검증이 끝날 때까지 지우지 말 것.**

### npz 스키마

| 필드 | 내용 |
|---|---|
| `images` | `(N, 64, 160)` uint8 — **정규화하지 않은 원본** |
| `subject` | `'m01'`~`'m58'` — **58-way 신원 라벨** |
| `frame_id` | 원본 프레임 번호 (**0-based**) |
| `event_id` | 이벤트 인덱스 |
| `blink_event` | 1 = blink 이벤트 프레임, 0 = unblink 이벤트 프레임 |
| `blink_confirmed` | `Right_Blink.csv`의 `Blink` (1 확정 / 0 가능성) |
| ~~`eye_closed`~~ | **만들지 않음** — 지속시간 라벨 부재 |

- `images`를 원본 uint8로 두는 것이 중요하다. 나중에 정규화를 시험하고 싶어지면 **npz를
  다시 만들 필요 없이** 로드 시점 변환으로 붙일 수 있다.
- `Blink=0` 이벤트도 넣되 `blink_confirmed=0`으로 표시 — 주 분석 제외, 민감도 분석용.
- 사용자별 로그(프레임 수, 결측 수, 버린 이벤트 수)를 `results/mebal2_build.json`에 기록.
- 이벤트 19프레임 중 결측 몇 개까지 허용할지 임계값을 **정하고 기록**할 것.

**예상 규모**: 58명 × 평균 248 이벤트 × 19프레임 ≈ 27만 프레임(양성). Eyeblink8의 35,496
프레임 대비 7.7배.

## Phase 3 — 58-way 신원 실험 (주력) ⬜

**목표 결과.** chance = 1/58 = **0.017** (Eyeblink8은 1/8 = 0.125였다).

비교군: `ours 벡터` / `EAR 스칼라` / `EAR 창 128프레임` / `EAR 창 요약통계` — §3.7(b)와 동일 구조.

**각오할 것**: 신원 수가 늘면 EAR은 chance 쪽으로 내려가는데 우리 벡터는 0.99대를 유지할
가능성이 높다. **격차가 좁아지는 게 아니라 벌어진다.** 나쁜 결과여도 그대로 보고한다.

### ⚠️ 설계상 미해결 두 가지

**(1) 한 사람당 세션이 하나뿐이다.**
같은 사람의 다른 날·다른 조명·다른 카메라 위치 녹화가 없다. 그래서 재식별 프로브의
train/test는 **어쩔 수 없이 같은 20분 연속 녹화 안에서** 갈린다. 그러면 프로브가
"누구인가"가 아니라 **"어느 세션인가"**(조명·카메라 각도·안경 반사·배경)를 맞출 수 있고,
58-way 정확도 0.99가 나와도 신원 누출의 증거로 단정할 수 없다.

현재 `identity_probe.py`는 프레임을 무작위 순열로 나눈다. 30 fps에서 인접 프레임은 거의
같은 이미지라 이 조건에서 특히 부풀려진다.

→ **대응**: 세션 앞 70% / 뒤 30%의 **시간 블록 분할**을 추가하고 무작위 분할과 나란히
보고한다. **두 숫자의 격차 자체가 "신원인가 세션인가"에 대한 답이다.**
(mEBAL1 38명과 신원이 겹치면 진짜 세션 간 재식별이 가능해진다 — 확인 가치 있음)

**(2) 실측 문서 Phase 3.2가 뒤집혀 있다.**
"58명 → 5-fold subject-disjoint, 같은 사람이 train/test에 걸치면 재식별 숫자가 무의미"라고
써 있는데, **폐쇄집합(closed-set) 재식별 프로브는 같은 사람이 양쪽에 있어야 성립한다.**
58-way 분류기를 학습하려면 58명 전원의 프레임이 train에 있어야 한다.

| 과제 | 올바른 분할 |
|---|---|
| 재식별 (프라이버시 축, 폐쇄집합) | **피험자 공유**, 프레임/시간 분리 |
| 깜빡임 분류 (유용성 축, Phase 4) | **피험자 분리** 5-fold |
| 재식별을 피험자 분리로 하려면 | 분류가 아니라 **검증(verification)**: 미지 신원 쌍이 같은 사람인가 |

이 둘을 섞으면 코드를 다시 짜게 된다. **Phase 1 전에 확정할 것.**

### 나머지 항목

- `train_disentangled.py`를 **양눈 64×160 + 58 신원으로 재학습**. 기존 λ 스윕은 인용 금지
- `recon_attack.py` 58명 재실행 — 공격자 학습 데이터가 늘어 **더 강한 공격**이 된다.
  대조군 3종(ours / mean / shuffled) 필수
- **파레토 곡선** — x축 privacy(58-way 재식별), y축 utility(Phase 4 분류 정확도).
  대조군 필수: EAR 스칼라, random projection(동일 차원), 평균벡터

## Phase 4 — 인스턴스 분류 (파레토의 유용성 축) ⬜

- 균형 1:1 blink / no-blink **이벤트** 분류. 19프레임 시퀀스 단위 (연속 평가가 아니라 인스턴스)
- **피험자 분리** 교차검증
- 대조군: `EAR + 고정임계` / `EAR + 동일 MLP + 동일 시간창` / `크롭 → 소형 CNN 직접`
  → **`EAR + 동일 MLP`를 못 이기면 기여는 "표현"이 아니라 "학습된 판정 규칙"이다.**
  이 대조군이 가장 아프고 가장 필요하다
- 보고: accuracy, PR-AUC, precision, fold 부트스트랩 CI
- **안경 착용/미착용 분리 보고** (아래 §7 참조). 라벨은 이 시점에 58명 수동으로 만든다

## Phase 5 — NIR (선택, 우선순위 낮음)

- NIR을 "저조도 강건성" 근거로 쓰지 말 것. RGB·NIR이 같은 조명에서 동시 촬영됐다
- 대신 **크로스모달 신원 누출**(NIR 표현이 RGB 신원을 흘리는가)이 disentanglement 주장에 직접 붙는다
- **NIR에는 랜드마크가 없다**(제공 랜드마크는 RGB 기준) → 별도 검출 필요
- `Left/Right_Infrared`는 **스테레오 좌우 뷰이지 눈의 좌우가 아니다**
- Right는 Left 대비 비트레이트 1/11 → 압축 아티팩트 먼저 확인

## 7.1 해결됨

## 7.2 미해결 — 기술

| 문제 | 상태 |
|---|---|
| **`zscore`/`rolling` 보정이 왜 나빠졌는가** | 원인 미규명. 윈도우 길이(150) 또는 에폭 선택을 보정 전 확률로 한 탓일 수 있음 |
| **임계값 격자 정의가 3벌** | `dim_sweep.py:180`, `ear_baseline.py:172`, `eval_events.py:47`이 각자 다른 격자 사용 |

| **재현성 미봉인** | 위 둘 때문에 **어떤 ± 숫자도 인용 불가**한 상태 |
| 07-30 작업분 전부 미커밋 | `results/*.json` 6개, `src/experiments/*.py` 3개 등 |
| mEBAL2 세션이 1인 1개 | 재식별 숫자가 세션 요인과 분리되지 않음 (§6 Phase 3) |
| Phase 3.2 분할 설계가 뒤집혀 있음 | 폐쇄집합 재식별에 subject-disjoint는 성립 불가 |

## 7.3 미해결 — 해석·서술

**(1) 어느 숫자가 현재값인지 자체가 불분명하다.**
`split_eval.json`은 Ours 0.854±0.226 vs EAR 0.878±0.206인데, 정정 문서는 조밀 격자로
Ours 0.803±0.321 vs EAR 0.977±0.035라고 한다. **격자를 통일하기 전에는 어느 쪽도 인용할 수 없다.**

**(2) 안경이 EAR 베이스라인을 부당하게 약화시킬 수 있다.**
mEBAL2 안경 착용률 32%. User 1(안경 착용자)에서 깜빡임 시 EAR이 40%만 하강한다(완전 폐안이면
더 떨어져야 함) — 렌즈 때문에 랜드마크가 눈꺼풀을 못 따라가는 것으로 보인다.

**위험한 이유는 편향 방향이 우리에게 유리하기 때문이다.** 우리 방법은 이미지 크롭을 직접
보므로 영향이 작은 반면 EAR은 랜드마크에만 의존하므로 더 크게 망가진다. mEBAL2에서
"우리가 EAR을 이겼다"가 나와도 **방법이 좋아서가 아니라 베이스라인이 불리해서**일 수 있다.
→ Phase 4에서 안경 착용/미착용 분리 보고.

**(3) 실측 문서 §7의 EAR 절대값이 우리 지표로 재현되지 않는다.**
문서는 0.273/0.210/0.214/0.357인데 리포지토리 6점 세트로는 0.241/0.185/0.188/0.315로
일관되게 13% 낮다(다른 인덱스 세트를 쓴 것). 결론은 같지만 **문서 숫자를 baseline 결과
옆에 인용하면 안 된다.**

**(4) 이벤트 수 불일치.** 공식 180명 10,550 blink vs 우리 배포본 58명 14,364 blink.
크롭 이미지 수와 CSV가 0.5% 안에서 일치하므로 CSV가 부풀려진 건 아니다. 공식 10,550이
논문 벤치마크용 균형 subset이고 배포 CSV에 더 넓은 라벨이 든 것으로 **추정**된다. 미해결.

# 9. 용어 사전

| 용어 | 뜻 |
|---|---|
| **EAR** | Eye Aspect Ratio. 눈꺼풀 상하 거리 ÷ 눈 가로 길이. 감으면 떨어진다. 학습 없는 표준 베이스라인 |
| **PERCLOS** | 단위 시간 중 눈이 (거의) 감겨 있던 시간 비율. 졸음·피로 지표. **지속시간 라벨이 필요** |
| **불완전 깜빡임** | 눈이 끝까지 감기지 않는 깜빡임. 안구건조증 지표 |
| **이벤트 recall** | 검출된 깜빡임 / 전체 깜빡임. 이벤트의 프레임 중 하나라도 맞으면 검출 |
| **frame false-alarm** | 비깜빡임 프레임에서 양성이 뜬 비율. precision 대리 지표 |
| **피험자 분리 분할** | 같은 사람이 train과 test에 동시에 없도록 나누는 것. 없으면 "외운 사람" 평가 |
| **선형 프로브** | 얼린 표현 위에 **선형 분류기 하나만** 얹어 재는 것. 표현에 정보가 얼마나 "쉽게" 들어 있나 |
| **재식별 (re-ID)** | 표현만 보고 누구인지 맞히기. 프라이버시 침해의 직접 지표 |
| **폐쇄집합 / 개방집합** | 후보 신원이 학습 때 본 N명 안에 있나(폐쇄) / 처음 보는 사람일 수 있나(개방) |
| **disentanglement** | 표현에서 특정 요인(신원)을 분리·제거하고 다른 요인(깜빡임)은 남기는 것 |
| **GRL** | Gradient Reversal Layer. 역전파에서 그래디언트 부호를 뒤집어 "맞히지 못하게" 학습시킨다 |
| **λ (람다)** | GRL의 세기. 유용성 ↔ 프라이버시 트레이드오프를 움직이는 손잡이 |
| **파레토 곡선** | λ를 훑으며 (프라이버시, 유용성) 점을 찍은 곡선. "공짜 구간"이 있는지를 본다 |
| **PSNR** | 복원 이미지 품질(dB). **단독으로는 무의미** — 평균 이미지도 높게 나온다. 대조군 필수 |
| **model inversion** | 표현에서 원본을 되돌리는 공격. 여기선 공격자 디코더 학습 |
| **p99 지연** | 100번 중 99번은 이 시간 안에 끝난다. 실시간성은 평균이 아니라 꼬리로 판단 |
| **governor** | 리눅스 CPU 주파수 정책. `performance`로 고정하지 않으면 벤치마크가 흔들린다 |
| **spin-wait** | ONNX Runtime이 다음 작업을 기다리며 CPU를 태우는 것. 인접 단계 측정을 27% 오염시켰다 |
| **NIR** | 근적외선. mEBAL2의 Left/Right는 **스테레오 좌우 뷰**이지 눈의 좌우가 아니다 |
