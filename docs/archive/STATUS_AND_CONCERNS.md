## 1. 지금 내가 생각하는 방향

- 눈 영상을 저장하지 않고 **벡터(숫자 코드)**로만 깜빡임을 검출하는 시스템.
- 프라이버시는 **구조에서** 나온다: 저장·전송은 벡터뿐, 디코더 미배포 → 원본 복원 불가.
- **라즈베리파이5 엣지**에서 실시간, ONNX 경량 모델.
- 입력은 **양눈 한 크롭(64×160) → 벡터 하나**.
- **신원 보호(disentanglement)와 데모 UI는 추후 연구/특허용**으로 분리.
- 최종 지향: 깜빡임을 primitive로 **눈 건강 위험 지표**(빈도·불완전 깜빡임·PERCLOS)까지, 논문 + 특허.
- **논문 타깃 = Letter(짧은 포맷)** → 기여를 **하나로 좁게** 잡아야 함.

## 2. 지도 의견 (교수님 / 박사님)

### 교수님 (연구 방향 제안)
- 현재 **MediaPipe 랜드마크 → EAR 깜빡임 검출**은 연구 확장성이 제한적. (MediaPipe + ONNX + low power vision = 엔지니어링 영역)
- 다른 Contribution을 고려하는 게 자연스럽다. **정보보호**가 연구 확장성이 좋다.
- 의료 쪽에서는 환자 정보를 **'비식별화(de-identification)'**라 표현. (원본 데이터의 **분포는 보존**하되 식별정보는 가리는 tabular 논문 예시 — 원본 분포를 유지하며 전혀 다른 데이터를 생성해 비식별화)
- 확장 제안 — 두 축:
  1. **유용성**: 깜빡임 검출 + 눈 피로/건조 위험도 분석 성능
  2. **정보보호**: 원본 복원 성능 + 사용자 식별 정확도
- → **"개인정보를 보호하면서 눈 건강 상태를 모니터링하는 엣지 AI 시스템"**
- 제목 제안: *On-Device Identity-Disentangled Representation Learning for Eye Health Monitoring*
  (**"Disentangled"** 단어 선호 — 최근 본인 논문에도 사용)

### 박사님 (스코프 조정)
- **개인정보(신원/disentanglement) 부분은 나중에 하자** → 지금은 그 앞단(**인코더·시스템**)에 집중.

### 기타 피드백 (출처 확인 필요)
- "눈이 둘인데 하나만 볼 이유가 없다. '그냥 해본다'는 이유가 아니다." → **양눈으로 전환**
- UI(눈 감지 표시·5초 캡처)는 **특허용 데모** 목적

## 3. 지금까지 한 것

- 파이프라인 전체 구축: `크롭 → 인코더(오토인코더) → 128벡터 → 판정(MLP) → 깜빡임`.
- 공개셋 **Eyeblink8** 처리(8명, 35,496 프레임). 수동 라벨 = EAR 독립 정답.
- **유용성(한쪽눈)**: 피험자 분리 val에서 이벤트 recall ~0.93, **EAR과 동급** 확인.
- **disentanglement PoC**(→추후 연구): 재식별 0.94→0.77 하락 시 깜빡임 AUC ~0.98 유지.
- **양눈 전환**(64×160) + 재생성·재학습 완료. (단 양눈은 false-alarm이 한쪽눈보다 높음)
- **엣지 예비**: ONNX 그래프 지연 0.12ms(모델은 사실상 공짜), 크롭이 병목, 데스크탑 기준 예산 내.
- 코드 패키지화(`src/...`), 문서화(OVERVIEW / PROJECT_DETAILED / RESULTS).

# ★ 내가 생각하는 문제점과 걱정

> 아래는 내가 실제로 걱정하는 점 + 함께 짚은 열린 질문들.

### (1) 너무 단순한 느낌
- 벡터로 뽑아 학습시키는 게 **너무 단순**하게 느껴진다.
- 사실 근거가 있음: "이미지→벡터→분류"는 딥러닝의 기본이고, 눈 임베딩→깜빡임 논문도 이미 존재(예: DE-ViViT).
  "원본 대신 임베딩으로 프라이버시"도 시선 추정 쪽에 선례가 있음. → **순수 ML 새로움으로는 얇다.**

### (2) "벡터가 왜 필요하냐"는 날카로운 질문
- "그냥 기기에서 깜빡임 계산하고 원본 안 남기면 되잖아?" 에 답이 있어야 함.
- EAR도 이미 복원 불가 압축 표현임. **벡터가 EAR보다 뭘 더 주는지**를 증명 못 하면 불필요한 중간단계로 보임.
- 후보 답: ① 한 벡터로 **여러 과제**(깜빡임+건강지표+시선) ② 어려운 조건(저조도·각도)에서 EAR보다 강함
  ③ (추후) disentanglement.

### (3) 깊이(=새로움)를 준 부분이 빠졌다
- **교수님의 방향(disentanglement/비식별화)**이 이 연구의 새로움이었는데, **박사님이 나중으로** 미룸 → 지금 남은 코어가 단순.
- **이게 letter 1편으로 충분한지, 데이터 오기 전 디딤돌인지** 불분명.
- Letter는 기여를 **하나로 좁혀야** 하는데, 그 하나가 무엇이 될지가 관건.

### (4) 프레이밍 미확정 (제일 중요)
- 이 논문의 기여를 **시스템·응용(프라이버시 엣지 눈 센싱) + 특허**로 갈지,
  **ML 새로움(disentanglement)**으로 갈지 안 정해짐.
- IEEE Sensors + 특허라면 **시스템 각도가 자연스럽고**, 그럼 ML이 단순해도 괜찮음(발명은 시스템·응용에 있음).
- ML 새로움 각도면 disentanglement(또는 "벡터>EAR" 증명)가 필요.

### (5) 데이터·검증이 아직 얇다
- 지금은 공개셋 1개(8명)·작은 val(2명·74이벤트)·단일 시드 → **예비 수준**.
- 양눈 전환 후 **false-alarm 상승**(128차원 병목 대비 이미지가 커서).
- **Pi5 실측 미완**(엣지 주장 아직 0% 실증).

### (6) 확인할 질문
1. **(교수님)** 이 letter의 기여를 **시스템·특허(프라이버시 엣지 눈 센싱)**로 갈지, **ML 새로움(disentanglement/비식별화)**으로 갈지? (깊이를 얼마나 파야 하는지 결정)
2. **(교수님/박사님)** 지금의 단순 코어가 **letter 1편**으로 충분한지, disentanglement 복귀가 **후속**인지?
3. **(박사님)** 신규 데이터셋 규모(피험자 수)와 자체 수집 병행 방향?
4. UI(특허 데모)를 언제 붙일지?
