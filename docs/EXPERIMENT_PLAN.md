## 1. 비교 대상

### 1-1. 공정 비교 조건 (모든 대조군 공통)

- 동일한 **피험자 분리 5-fold** (`src/v2/common/folds_5fold.json`, 이벤트 수 + 배치 이중 층화, 57명)
- 동일한 **3 seed** (0, 1, 2). 단일 시드 비교 금지
- 동일한 **이벤트 집합** — 유효 이벤트 27,758. EAR 이 정의 불가로 빠뜨린 210개는
  양쪽을 같은 집합으로 맞춰 비교 (`docs/v2/PROTOCOL.md` §10 S6)
- 동일한 **임계값 격자** (`src/v2/common/thresholds.py`). 실험 스크립트가 격자를 새로 만들면 규칙 위반
- 동일한 **조기 중단 규칙**. 고정 에폭 vs 조기 중단이 섞이면 비교가 무효
- 동일한 **입력 정규화** — 프레임 단위 표준화 `(x − mean) / std`
- val 에서 고르고 val 에서 보고하지 않는다
- 판정은 **짝지은 피험자 클러스터 부트스트랩** 으로 (ours − baseline) 차이의 95% CI 를 낸다

## 3. 학습 및 검증 데이터 분할

| 항목 | 값 |
|---|---|
| 분할 단위 | **피험자** (같은 사람이 train 과 test 에 동시에 들어가지 않는다) |
| fold | **5-fold**, 이벤트 수 + 배치(2020/2022) **이중 층화**, 57명 🔒 |
| 얼린 배정 | `src/v2/common/folds_5fold.json` — `freeze_folds` 는 `force=True` 없이 덮어쓰지 않는다 |
| seed | 0, 1, 2 (최소 3) |
| val | train fold 안에서 다시 피험자 분리. **val 에서 고르고 val 에서 보고하지 않는다** |
| 총 런 | 조건당 5 fold × 3 seed = **15런** (약 4.5시간/조건, RTX 급 GPU 기준) |
| 재식별 프로브 분할 | ▶ 논문 범위 밖 (`PATENT_AND_FUTURE_WORK.md`) |

> **비용 관리** — 대조군이 늘면 15런 × N 이 된다. B3·B5·B6 는 먼저
> **fold 0·1 × 3 seed(6런)** 로 탐색하고, 논문 표에 넣을 것만 5 fold × 3 seed 로 확정한다.
> **탐색 단계 숫자는 확정 값으로 인용하지 않는다.**

### 4-4. 서브그룹 보고 규칙 🔒

### 5-1. 분류 성능

| 지표 | 역할 |
|---|---|
| **PR-AUC** | 🔒 **주 지표.** 임계값 선택과 무관. 판정은 이것으로만 |
| ROC-AUC | 함께 보고 (판정에는 쓰지 않음) |
| Accuracy | 함께 보고 |
| Precision | 함께 보고 |
| Recall | 함께 보고 — ⚠️ **현재 미계산** |
| F1-score | 함께 보고 — ⚠️ **현재 미계산** |
| 판정 규칙 | (ours − baseline) PR-AUC 차이의 **짝지은 피험자 클러스터 부트스트랩 95% CI 하한 > −δ**, δ = **0.02** 🔒 |

> δ=0.02 의 근거 — EAR 베이스라인의 fold 간 변동이 ROC-AUC 0.0166 / PR-AUC 0.0203 /
> accuracy 0.0190 으로 모두 0.02 근처였다. **우리 결과가 0건인 시점에 확정됐다. 재협상 없음.**
>
> 🔴 **`results/v2/train_encoder.json` 의 각 런은 `accuracy · precision · pr_auc · roc_auc · thr`
> 만 저장한다. Recall 과 F1 은 계산되지 않았다.** 논문 Table I 에 넣으려면
> `train_encoder.py` 의 지표 계산부에 추가하고 재실행(또는 저장된 점수 사이드카에서
> 후처리)해야 한다. → `TASKS.md` T3-6 재실행에 함께 포함시킨다.

| **MMAC (프레임당)** | `src/v2/model/encoder.py` `analyse()` 로 산출 가능 | ⚠️ 코드는 있음, 보고 안 됨 |
| **프레임당 추론 시간** | ONNX 그래프 단독 (`bench_latency.py` 상당) | ❌ v2 미측정 |
| **전체 파이프라인 지연 시간** | read → detect → crop → infer, p50/p95/**p99** | ⚠️ v1 만 |
| **FPS** | 5분 지속 처리량 (sustained) | ⚠️ v1 만 |
| **메모리 사용량** | RSS peak (MB) | ⚠️ v1 만 (218.9 MB) |
| **CPU 사용량** | 평균 % (4코어 기준 최대 400%) | ⚠️ v1 만 (148.6%) |
| **온도 · 스로틀** | 시작/종료 온도, throttled 플래그 | ⚠️ v1 만 (49.4→57.6℃, 플래그 없음) |

> 🔴 **v1 Pi 5 수치는 인용 금지.** `results/pi_ours.json` 의 e2e p99 12.06 ms / 86.07 fps 는
> **v1 인코더(128차원 오토인코더) + 640×480 클립** 기준이다. v2 는 인코더 구조가 다르고
> mEBAL2 는 1280×720 이다. PROTOCOL §13: *"지연시간은 v2 에서 새로 측정한 것만 인용한다."*

### 5-3. 이번 논문에서 측정하지 않는 지표

- 재식별 정확도 (▶ `PATENT_AND_FUTURE_WORK.md`)
- 복원 PSNR / MAE / 복원본 재식별 (▶ 같은 문서)
- 유용성-프라이버시 파레토 (▶ 같은 문서)
- PERCLOS · 불완전 깜빡임 비율 (데이터가 허용하지 않음)
- 연속 영상 event recall · frame false-alarm (라벨 커버리지 문제)

## 6. Raspberry Pi 5 실험 계획

### 6-1. 측정 환경 (v1 에서 확립된 것 — 그대로 유지)

| 항목 | 값 |
|---|---|
| 보드 | Raspberry Pi 5 Model B Rev 1.1 / 16 GB / **액티브 쿨러(pwm-fan)** |
| OS | Debian 13 trixie, 커널 6.18 |
| Python | **3.11** (conda/Miniforge). 시스템 3.13 에는 mediapipe aarch64 휠이 없다 |
| 런타임 | onnxruntime ≥ 1.18.0 (IR version 10), mediapipe 0.10.18, OpenCV 4.11 (NEON FP16), numpy 1.26.4 |
| 실행 옵션 | `--intra-threads 2 --no-spin` — **선택이 아니다.** 빼면 ONNX 스레드가 spin-wait 하며 디코딩·검출을 27% 느리게 만들어 EAR 비교가 무효가 된다 |
| CPU governor | 측정 전 `performance` 로 고정 (재부팅하면 ondemand 로 돌아간다) |
| 측정 길이 | 각 모드 **5분** 지속 |

### 6-2. v2 에서 새로 해야 할 것

| # | 작업 | 상태 |
|---|---|---|
| P1 | v2 encoder + 시간 헤드 + 판정 헤드를 **ONNX 로 export** (`src/v2/` 경로에 새로 작성) | ❌ 미착수 |
| P2 | ✅ **입력 해상도 확정 (2026-08-05)** — **주 = 640×480 @ 30 fps**, **보조 = 1280×720**. 근거는 아래 §6-4 | ✅ 결정 완료 |
| P3 | `run_video.py` 를 v2 파이프라인으로 이식 (`--mode ours|ear|image_cnn`) | ❌ 미착수 |
| P4 | 3자 비교 실측 — ours / ear / image_cnn 각 5분 | ❌ 미착수 |
| P5 | PC(GPU·CPU) 환경과 Pi 5 결과 비교표 | ❌ 미착수 |
| P6 | 필요 시 양자화(INT8) 또는 모델 최적화 적용 후 재측정 | 조건부 |

> **P4 가 논문 표의 핵심이다.** ear 모드와 image_cnn 모드를 같은 하네스·같은 클립·같은
> 옵션으로 재야 비교가 성립한다.
>
> **P6 는 필요할 때만.** v1 에서 e2e p99 가 예산의 36% 였다. 여유가 크면 양자화는
> 기여를 늘리지 않고 지면만 먹는다.

### 6-3. 입력 해상도 — 🔵 확정 (2026-08-05)

문헌 조사 결과 **640×480 @ 30 fps 가 이 분야의 사실상 표준**이다.

| 근거 | 값 |
|---|---|
| Raspberry Pi 5 기반 졸음 검출 데이터셋 (2025) | **640×480, 30 fps**, H.264 |
| PiCamera 기반 EAR 깜빡임 검출 구현들 | **640×480**, 최대 32 fps |
| Eyeblink8 (우리 v1 측정 클립) | **640×480**, 408 blinks / 70,992 frames |
| 일부 데이터셋 (정면·안경·상방 시선) | 320×240, 30 fps |
| mEBAL2 (우리 v2 학습 데이터) | 1280×720 |

**결정**

- **주 측정: 640×480 @ 30 fps.** Table II 의 기준값. 선행 연구와 직접 비교되고,
  v1 측정과 같은 조건이라 **인코더 변경의 효과만 분리**된다.
- **보조 측정: 1280×720.** "학습 데이터와 같은 해상도에서도 도는가"에 답한다.
- 두 해상도 × 3 모드(ours / ear / image_cnn) = 6런 × 5분.

> ⚠️ **해상도가 오르면 얼굴 검출이 지배적이 된다.** v1 640×480 에서 detect 가
> e2e 의 약 67%(7.76 / 11.53 ms p50)였다. 720p 에서는 더 커져 **encoder 비용 차이가 묻힌다.**
> → **단계별 분해(read / detect / crop / infer)를 반드시 함께 보고한다.**

> 출처(전부 [검색요약], **논문 인용 전 원문 확인 필요**):
> [Raspberry Pi 5 졸음 검출 데이터셋 (PMC)](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12630088/) ·
> [PyImageSearch — Pi facial landmarks + drowsiness](https://pyimagesearch.com/2017/10/23/raspberry-pi-facial-landmarks-drowsiness-detection-with-opencv-and-dlib/) ·
> [Embedded System for Eye Blink Detection (IEEE)](https://ieeexplore.ieee.org/document/9509908/)

### 6-4. 완료 조건 (게이트)

| 게이트 | 기준 |
|---|---|
| **G-E1 실시간** | v2 encoder 기준 e2e **p99 ≤ 33.3 ms** (30 fps 예산), 5분 지속, throttled 플래그 없음 |
| **G-E2 3자 비교** | ours / ear / image_cnn 세 모드가 **같은 하네스 · 같은 클립 · 같은 옵션**으로 측정됨 |
| **G-E3 경량화 보고** | 파라미터 수 · 파일 크기 · MMAC · RSS peak · CPU% 를 세 방법 전부에 대해 보고 |

> G-E1 을 통과하지 못하면 양자화(P6)로 간다. 그래도 안 되면 **입력 해상도를 낮추는 것이
> 다음 수단**이며, 그 경우 검출 성능 재측정이 연쇄된다.

## 9. 실험 위생 — 반복하지 말 것

`docs/v2/PROTOCOL.md` 부록에서 이번 방향에도 그대로 적용되는 항목.

1. 실험 스크립트마다 임계값 격자를 따로 만들지 말 것 (`src/v2/common/thresholds.py` 만)
2. 격자를 근사하지 말 것 (표본 5만 이하면 유일값 전체)
3. 단일 시드로 baseline 과 비교하지 말 것 (최소 3 seed)
4. val 에서 고르고 val 에서 보고하지 말 것
5. 봉인 안 된 런의 ± 를 인용하지 말 것
6. **새 실험은 대조군을 먼저 정할 것**
7. **결과가 유리하면 베이스라인이 불리해진 것은 아닌지 먼저 의심할 것** — 이 프로젝트에서
   우위가 +0.1058 → +0.0323 → +0.0151 로 두 번 줄었다
8. n=1 값을 전체 값처럼 쓰지 말 것
9. 한 명이 그룹 결론을 끌고 가지 않는지 확인할 것 (leave-one-out 병기)
10. 게이트가 검사 대상을 쓰지 않는지 확인할 것
11. 피험자 평균을 서브그룹의 주 숫자로 쓰지 말 것
12. 새 스크립트를 짜기 전에 같은 일을 하는 스크립트가 이미 있는지 먼저 확인할 것
13. 문서가 아니라 파일을 열어 확인할 것
