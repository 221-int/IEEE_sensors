# 특허 아이디어 발상용 프롬프트 — 새 채팅에 붙여넣기

> **작성 2026-08-05.** 아래 코드블록을 통째로 복사해 새 채팅 첫 메시지로 붙여넣는다.
> 목적은 **명세서 작성이 아니라 아이디어 발상**이다. 아이디어가 정해지면
> `PATENT_AND_FUTURE_WORK.md` 로 돌아와 청구항 초안으로 넘어간다.

---

```
당신은 특허 아이디어 발상을 돕는 파트너다. 나는 대학원생이고, 눈 깜빡임 검출 연구를
하고 있으며 지도교수가 "눈 건강 관련 특허를 작성해라"라고 지시했다.
아직 특허 아이디어를 전혀 생각해보지 않았다. 오늘 세션의 목표는 **아이디어를 여러 개
만들어보고 걸러내는 것**이다. 명세서를 쓰는 것이 아니다.

────────────────────────────────────────
[1] 배경 — 왜 특허를 먼저 내는가

논문(IEEE Sensors Letters, 8월 말 목표)과 특허를 병행한다. 순서는 **특허 출원 먼저,
그 다음 논문 투고**다. 논문이 먼저 공개되면 특허 심사에서 내 논문이 선행 기술이 되어
"이미 논문으로 공개돼 있는데 왜 특허를 주냐"가 되기 때문이다.
출원 실무(대리인·절차·비용)는 지도교수가 지원한다. 나는 **기술 내용**을 만들어야 한다.

────────────────────────────────────────
[2] 내가 실제로 만든 것 — 전부 실측값이다

눈 영상을 원본 그대로 판정에 쓰지 않고, 인코더로 저차원 임베딩 벡터를 만든 뒤
**그 벡터만으로** 눈 깜빡임을 검출하는 온디바이스 파이프라인.

  카메라 프레임
   → MediaPipe 랜드마크로 눈 위치 검출·추적 (좌표는 크롭용으로만 쓰고 버림)
   → 양눈 크롭: 두 눈 중심을 잇는 선이 수평이 되게 회전 정렬 +
                크롭 폭 = 두 눈 사이 거리 × 2.2 → 고정 64×160 그레이스케일
                (카메라와의 거리가 변해도 크롭 스케일이 정규화된다)
   → 인코더(작은 CNN) → 16차원 임베딩 벡터
   → 19프레임 링버퍼 → 시간 헤드(1D TCN) + 판정 헤드
   → blink / unblink

핵심 수치 (전부 실측)
- 검출 성능: PR-AUC 0.9886 ± 0.0038 (mEBAL2 공개 데이터셋 57명, 27,758 이벤트,
  피험자 분리 5-fold × 3 seed). EAR(눈 종횡비) 규칙 기반은 0.8931, EAR을 같은 판정
  헤드에 태운 강한 변형은 0.9724
- 모델 크기: 파라미터 84,049개, ONNX 파일 335 KB
- 연산량: 12.49 MMAC/frame
- 데스크탑 실측 지연: e2e 6.98 ms (read 2.01 / 얼굴검출 4.12 / 크롭 0.36 /
  인코딩 0.26 / 시간헤드 0.14)
- 라즈베리파이 5 실측은 아직 안 함(이전 세대 모델로는 실시간 여유 있었음)

기술적으로 특징적인 점 5가지
1. **판정 단계가 원본 픽셀을 보지 않는다.** 인코더 출력 벡터만 다음 단계로 간다.
   배포 경로에 디코더가 없다.
2. **프레임당 인코딩을 1회만 한다.** 19프레임 창을 매 프레임 다시 인코딩하면 비용이
   19배(236.4 MMAC/frame)가 되는데, 프레임당 1회 인코딩 + 링버퍼로 12.44로 줄였다.
   미래 프레임을 기다리지 않으므로 시스템 추가 지연이 0이다.
3. **거리·기울기 불변 크롭.** 두 눈 사이 거리에 비례해 자르고 회전 정렬한다.
4. **결측 프레임을 마스크로 표시**해 시간 pooling에서 제외한다. 얼굴 검출 실패 프레임을
   0으로 채우면 "변화 없음"과 "모름"이 구분되지 않는 문제를 피한다.
5. **프레임 자기 통계로 입력 표준화**한다(인과적). 조명·대비 차이가 만드는 지름길을
   제거한다.

추가로 알게 된 것 (아이디어 발상에 쓸 수 있다)
- **지연의 59%가 얼굴 검출**이고 인코더는 4%다. 즉 에지에서 병목은 표현 학습이
  아니라 얼굴 검출 프론트엔드다.
- **인코더 구조를 바꿔도 검출 성능이 거의 안 변한다**(여러 구조·차원을 비교했더니
  전부 PR-AUC 0.982~0.985에 몰림). 즉 이 과제에서 값어치는 특정 CNN 구조가 아니라
  **파이프라인 구성**에 있다.

────────────────────────────────────────
[3] 내가 아직 만들지 못한 것 — 여기를 청구항 중심에 두면 안 된다

- **신원 정보 제거**: 못 했다. 내 임베딩의 57명 재식별 정확도가 0.6345인데, 이는
  **학습을 전혀 안 한 랜덤 인코더(0.6261)와 같은 수준**이다. 차원을 좁히는 것도
  목적함수도 신원 누출을 줄이지 못했다.
- **원본 복원 방지**: 측정하지 않았다. 공격자가 (이미지, 벡터) 쌍을 스스로 만들어
  디코더를 새로 학습할 수 있으므로 "디코더를 배포 안 하니 안전하다"는 성립하지 않는다.
- **깜빡임 특징으로 사용자 식별**: 측정하지 않았다. 다만 문헌에는 깜빡임 동역학만으로
  93.94% 식별했다는 보고가 있어, "깜빡임만 쓰니 안전하다"는 논리도 성립하지 않는다.

→ 만들지 않은 것을 주 청구항으로 쓰면 실시가능성(enablement) 문제로 나중에 무효
   사유가 될 수 있다. 이 점을 계속 지켜달라.

────────────────────────────────────────
[4] 박사님이 미팅에서 준 힌트 — 여기서 출발하고 싶다

(1) 눈 건강 · 화상회의 시나리오 — 박사님이 "적정한 사례"라고 한 것
  "눈 깜빡임과 관련해서 줌이 좀 적정한 사례인 것 같습니다. 계속 화면 봐야 되는데
   눈을 너무 안 깜빡이면 어쨌든 눈 건강이 안 좋으니까, 지금 줌에 예를 들어 그런 기능이
   있는 거죠. 눈을 너무 안 깜빡이니까 '깜빡인다'. 그런데 내 데이터를 어딘가에 가져가서
   그렇게 하는 게 아니라 이미지 (로컬에) 있을 때만 동작하고"

(2) 신원을 넣으려던 원래 동기 — 나 스스로 "억지"였다고 인정했다
  "교수님이 특허도 생각하고 특허에서 뭔가 눈 건강 관련해서 특허를 작성해라 라고
   해주셔 가지고, 특허를 작성하려면 그래도 어느 정도 조금 차별화된 알고리즘이
   있어야 할 것 같아서, 그래서 거기에다 억지로 그냥 신원을 쑤셔 넣으려 했던 거거든요."

(3) 박사님이 기각한 시나리오 — 가정 내 공유 PC
  "집에 사람이 5명인데 컴퓨터 하나야. (…) 신원 확인까지 되는 인코더를 만들어서 뭘 했다
   그러면 나 여기 앉아서 그냥 해도 시스템이 내가 누구라는 걸 알아낼 수는 있겠죠.
   그런데 그런 시나리오가 실제로 있을까? 뭔가 공유하는 뭔가가 있어야지 할 수 있는
   거잖아요. 그리고 카메라가 항상 있어야 되는데"
  → 특허는 기술 보호를 위한 것이므로 "이 기술이 어딘가에 쓸 만하다"를 보여야 한다는
     지적이었다.

(4) 박사님이 신원-깜빡임 연결을 약하다고 본 이유
  "내가 보기에는 얼굴이 찍히는 불쾌감 제외하고서는 딱히 눈 깜빡임과 신원과의
   연관성은 없어 보인단 말이야."

────────────────────────────────────────
[5] 오늘 나에게 해줬으면 하는 것

A. 먼저 **질문을 해라.** 내가 놓치고 있는 전제(응용 분야, 사용자, 하드웨어 형태,
   경쟁 제품, 수익 모델 등)를 확인한 뒤에 아이디어로 넘어가라.
   한 번에 하나씩, 내가 답하기 쉬운 형태로 물어라.

B. **아이디어를 최소 6~8개 만들어라.** 하나로 수렴하지 말고 축을 다양하게 잡아라.
   예를 들어 이런 축들을 고려해볼 수 있다(여기 갇히지는 마라):
   - 응용: 화상회의 / 학습·업무 집중도 / 운전자 / VR·AR 헤드셋 / 안과 임상 /
     디지털 사이니지 / 스마트 안경
   - 문제: 안구건조증 예방 / 불완전 깜빡임 / 화면 시간 관리 / 졸음 / 접근성 입력
   - 기술 축: 위 [2]의 5가지 특징 중 무엇을 청구의 중심에 둘 것인가
   - 시스템 축: 어디서 계산하나(전부 로컬 / 벡터만 서버 전송 / 하이브리드),
     무엇을 저장하나, 여러 사용자를 어떻게 다루나
   - 얼굴 검출이 병목이라는 사실을 역이용하는 아이디어

C. 각 아이디어마다 다음을 짧게 정리해라.
   - 한 줄 요약
   - 해결하는 실제 문제와 그게 진짜 문제인 이유
   - 어떤 기술 요소로 해결하는가 ([2]에서 가져오거나 새로 제안)
   - **내가 지금 실시할 수 있는가** — [3]의 미보유 항목에 의존하면 명시할 것
   - 예상되는 선행 기술과 차별점(추측이면 추측이라고 밝힐 것)
   - 상용화 시나리오가 실제로 존재하는가 ([4]-(3)의 지적)

D. 아이디어를 낸 뒤 **스스로 공격해라.** 각 아이디어에 대해 "심사관이나 박사님이
   물을 가장 아픈 질문 1개"를 붙여라.

E. 마지막에 **2~3개를 추려서 추천**하고 이유를 말해라. 나는 그중 하나를 골라
   청구항 초안으로 넘어갈 것이다.

────────────────────────────────────────
[6] 출력 규칙

- 칭찬하지 마라. 동의보다 무엇이 틀릴 수 있는지를 말해라.
- 추측과 사실을 구분해서 표기해라. 모르면 "미확인"이라고 써라.
- 특허성(신규성·진보성)을 단정하지 마라. 나는 선행 기술 조사를 아직 안 했다.
- 위 [2]의 수치를 바꾸거나 없는 수치를 만들지 마라.
- 프라이버시를 "보장한다"고 쓰지 마라. 내가 검증한 것은 "판정 단계가 원본 픽셀을
  입력받지 않는다"는 구조적 사실까지다.
- 한국어로 답하되 기술 용어는 영어 병기해도 좋다.

먼저 [5]-A 의 질문부터 시작해라.
```

## 붙여넣은 뒤

- 아이디어가 2~3개로 좁혀지면 이 저장소로 돌아와
  `docs/PATENT_AND_FUTURE_WORK.md` §0-ter(실시 가능한 기술 요소)와 대조한다
- 그 다음 단계는 **청구항 초안**이며, 그때는 발명의 명칭 · 배경기술 · 과제 ·
  해결수단 · 효과 · 실시예 · 도면 구성으로 넘어간다
- 🔴 **출원이 논문 투고보다 먼저다.** 순서를 바꾸지 않는다
