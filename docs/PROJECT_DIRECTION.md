# PROJECT_DIRECTION — 연구 방향의 현재값

> **작성 2026-08-05.** 근거는 같은 날 진행된 연구 미팅 전사문이다.
> 이 문서와 `docs/v2/PROTOCOL.md` §14·§15 가 충돌하면 **이 문서가 현재값**이다.
> PROTOCOL 의 측정 규칙(임계값 격자 · 시드 · 분할 · chance 보고 · 대조군 정의)은
> 그대로 유효하며, 폐기된 것은 **연구 범위**뿐이다.

---

## 0. 한 문장

**원본 눈 이미지를 판정 단계에서 쓰지 않고, encoder 가 만든 embedding vector 만으로
eye blink detection 을 수행하는 경량 모델을 만들고, 그것이 Raspberry Pi 5 같은
edge device 에서 실시간으로 동작함을 보인다.**

---

## 1. 이전 연구 방향 (2026-08-04 까지)

`docs/v2/PROTOCOL.md` §0 (2026-08-04 판) 기준.

| 구분 | 내용 |
|---|---|
| 최종 목표 | **encoder 단에서 신원 재식별을 불가능하게 만드는 것 = 프라이버시 확보** |
| 프라이버시 주 근거 | **복원 장벽** (PROTOCOL §14) — 공격자 디코더가 원본을 복원하지 못함 |
| 프라이버시 보조 지표 | 재식별 정확도 (PROTOCOL §11 Phase 5) |
| 유용성(눈 깜빡임 검출) | **주장이 아니라 전제 조건.** EAR 비열등(δ=0.02)만 넘기면 됨 |
| 이번 라운드 필수 게이트 | G-R2 (복원본 재식별 < 0.454), G-P1 (재식별 < 0.086), G-P2, G-P3 |
| encoder 확정 시점 | 억제 기전(GRL λ) + D 파레토를 돌린 **맨 뒤** |
| 교수님 제안 제목 | *On-Device Identity-Disentangled Representation Learning for Eye Health Monitoring* |

즉 **눈 깜빡임 검출 + 신원 식별/제거 + 프라이버시 보호를 한 논문에서 모두 해결**하는 구성이었다.

## 2. 기존 방향에서 발생한 문제

전사문에서 지적된 것을 그대로 옮긴다.

### 2-1. 눈 깜빡임과 신원 사이에 논리적 연결이 약하다

> "내가 보기에는 얼굴이 찍히는 불쾌감 제외하고서는 딱히 눈 깜빡임과 신원과의 연관성은 없어 보인단 말이야."
> — 전사문 07:40

신원 억제는 **얼굴 인식 · 홍채 · 동공** 과제에서 자연스러운 목표지, 눈 깜빡임 검출 과제의
목표로 붙이면 억지가 된다. 본인도 같은 인식이었다.

> "눈 깜빡임으로 하다가 (…) 계속 생각하다 보니까 눈 깜빡임이랑 (…) 의미가 약간 좀 연결이 잘 안 되는 느낌"
> — 전사문 08:19

### 2-2. 두 가지를 합치면 검증할 것이 너무 많다

> "두 개가 너무 한 번에 어떻게 잘 묶여질지를 잘 모르겠어요. 검증해서 뭔가 보여줘야 하는 게 너무 많을 것 같은데"
> — 전사문 05:12

실제로 PROTOCOL 은 이번 라운드에 게이트를 4개(G-R1·G-R2·G-P1·G-P2·G-P3) 더 요구했고,
Phase 5-bis(복원 장벽)와 Phase 7(억제·파레토)은 **둘 다 스크립트조차 없는 상태**였다.
재식별 0.6345 에서 게이트 0.086 까지 **7.4배** 격차가 있었다.

### 2-3. IEEE Sensors Letters 4페이지에 들어가지 않는다

> "센서스 레터지는 4페이지였잖아요. 그거 어떻게 답합니까?"
> "인트로부터 릴레이티드 워크 쓰면 한 페이지는 넘어가고, 메소드도 그림을 넣어야 되고,
> Overall Architecture 넣고 설명 쓰고 실험 파트에서 실험 결과 그래프 몇 개 넣으면 진짜 공간이 없어요."
> — 전사문 08:51, 09:07

### 2-4. 신원 억제를 밀어붙인 실제 동기는 논문이 아니라 특허였다

> "그 신원을 계속 생각한 이유가 교수님이 특허도 생각하고 (…) 특허를 작성하려면 어느 정도 차별화된
> 알고리즘이 있어야 할 것 같아서 그래서 거기에다 억지로 그냥 신원을 쑤셔 넣으려 했던 거거든요."
> — 전사문 12:50

→ 동기가 특허라면 **특허에 넣으면 된다.** 논문에 넣을 이유가 아니다.

### 3-2. 이전 방향과의 대비

| 축 | 이전 (~2026-08-04) | 현재 (2026-08-05~) |
|---|---|---|
| 논문 주장 | 유용성 동등을 전제로 **신원 노출량을 정량화**한다 | **embedding vector 만으로 눈 깜빡임을 검출하고, 에지에서 실시간으로 돈다** |

| EAR 의 위상 | 유용성 베이스라인 | **주 비교 대상 중 하나** (이미지 기반 모델과 함께) |

| 신원 재식별 | 보조 지표, 이번 라운드 게이트 | **논문 범위 밖 → 특허·후속 연구** |
| 복원 장벽 | 프라이버시 **주 근거**, 이번 라운드 필수 | **논문 범위 밖 → 특허·후속 연구** |
| 억제(GRL)·파레토 | 이번 라운드 포함, encoder 확정의 전제 | **논문 범위 밖 → 후속 연구** |
| encoder D·목적함수 확정 시점 | Phase 7 파레토 이후 | **눈 깜빡임 성능 + 에지 비용으로 확정 가능** |
| Pi 5 측정 | 맨 뒤 (확정 encoder 이후) | **주 기여의 일부. 앞으로 당긴다** |
| 판정 기준 | 비열등 (δ=0.02) | 비열등은 하한으로 유지 + **조건별 강건성**과 **비용**이 주 논거 |

## 4. 현재 논문 범위 (IEEE Sensors Letters)

**포함한다.**

1. encoder → embedding vector → 판정 헤드의 눈 깜빡임 검출 파이프라인 (Overall Architecture)
2. EAR 기반 방법과의 동일 조건 비교
3. 원본 이미지 기반 분류 모델과의 동일 조건 비교
4. 다양한 조건(조도 · 얼굴 각도 · 눈 위치 · 거리 · 안경 · 부분 깜빡임)에서의 강건성 비교
5. 경량화 지표 — 파라미터 수 · 모델 크기 · MMAC · 메모리
6. Raspberry Pi 5 실측 — 프레임당 추론 시간 · 파이프라인 지연 · FPS · CPU 사용량
7. 판정 단계에서 원본 이미지를 쓰지 않는 **구조적** 서술 (한두 문장, 주장이 아니라 설계 설명)

**제외한다.**

## 5. 프라이버시 관련 서술의 허용 범위 🔴

이번 논문에서 **쓸 수 있는 문장**:

- "판정 단계는 원본 눈 이미지가 아니라 encoder 가 만든 D차원 embedding vector 만 입력으로 받는다."
- "배포되는 파이프라인에는 디코더가 포함되지 않는다."
- "원본 프레임을 저장하거나 전송하지 않는 구성이 가능하다."

**쓸 수 없는 문장** (검증하지 않았다):

- ❌ "우리 표현은 신원 정보를 담지 않는다"
- ❌ "embedding vector 로부터 원본 이미지를 복원할 수 없다"
- ❌ "프라이버시를 보장한다 / 프라이버시 보호 기법을 제안한다"
- ❌ "디코더 공격을 방어한다"

**실측이 이 금지를 강제한다.** `results/v2/phase5_reid.json` 에서 우리 embedding vector 의
57-way 재식별은 **0.6345 ± 0.0288** (균등 chance 0.0175 대비 36배)이고, **학습을 전혀 하지
않은 랜덤 인코더(0.6261)와 같은 수준**이다. 즉 현재 encoder 는 신원을 그대로 흘린다.
논문에서 프라이버시를 주장하면 이 파일이 곧바로 반증이 된다.

또한 `docs/v2/RELATED_WORK.md` §E 에 따르면 **깜빡임 동역학 단독으로도 93.94% 식별**된
선행 연구가 있으므로, "깜빡임 신호만 쓰니까 안전하다"는 논리도 성립하지 않는다.

> 신원 제거나 복원 불가능성을 입증했다고 쓰지 않는다.

## 7. 연구 가설

`RESEARCH_PLAN.md` §4 에서 확인된 사실 / 가설 / 검증 대상으로 나누어 자세히 다룬다. 요약:

- **H1** — embedding vector 는 EAR 스칼라가 담지 못하는 영상 특징(눈 모양, 눈꺼풀 상태,
  주변 밝기, 눈 주변 질감, 부분적 자세 변화, 감기는 과정)을 담는다. **미검증.**
- **H2** — 그 결과 저조도 · 얼굴 각도 변화 · 부분 깜빡임에서 EAR 보다 성능 저하가 작다. **미검증.**
- **H3** — encoder 를 한 단 더 통과해도 원본 이미지 기반 모델 대비 지연·FPS 손실이
  edge device 실시간 예산 안에 들어간다. **미검증** (v1 인코더 기준 예비 근거만 있음).

## 8. 예상 기여점

미팅에서 합의된 형태 (전사문 03:11, 08:56, 10:29).

1. 눈 깜빡임 검출을 **원본 이미지가 아닌 encoder embedding vector 위에서** 수행하는
   파이프라인을 제시하고, 동일 조건에서 EAR 및 이미지 기반 모델과 비교한다.
2. 깜빡임 검출 과제의 **알려진 실패 조건**(저조도 · 얼굴 각도 · 안경 · 부분 깜빡임)에서
   세 방법의 성능을 같은 프로토콜로 비교한다.
3. 파라미터 수 · 모델 크기 · 추론 시간 · FPS · 메모리를 함께 보고하고, **Raspberry Pi 5
   실측**으로 실시간 동작을 확인한다.
