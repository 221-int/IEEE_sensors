  - 목적: PROTOCOL §0 에서 🔓 해제된 D 를 새 기준(성능 + edge 비용)으로 다시 잠근다
  - 🔴 **D=16 의 원래 근거가 무효화됐다.** v1 스윕(8명·한쪽눈)은 인용 금지이고,
    "작은 D 가 신원을 덜 흘린다"는 기대는 **실측으로 기각**됐다
    (512→32 로 16배 좁혀도 선형 재식별 0.9992→0.9947). 프라이버시가 범위 밖이 된
    지금 **D 를 작게 유지할 이유가 남아 있지 않다**
  - 🔴 **D 를 키우는 비용이 거의 0이다** (`E.analyse()` 실측):

    | D | conv MMAC | fc MMAC | 총 MMAC | fc 비중 |
    |---:|---:|---:|---:|---:|
    | 8 | 12.41 | 0.016 | 12.43 | 0.13% |
    | **16** (현재) | 12.41 | 0.033 | **12.44** | 0.26% |
    | 32 | 12.41 | 0.066 | 12.48 | 0.53% |
    | 64 | 12.41 | 0.131 | 12.54 | 1.05% |
    | 128 | 12.41 | 0.262 | 12.67 | **2.07%** |

    conv 가 12.41 로 고정이라 **D=128 이어도 총 연산이 1.8% 늘 뿐**이다
  - 스윕: **D ∈ {8, 16, 32, 64}** (기존 {8,16,32} 에서 확장), fold 0·1 × 3 seed
  - 완료 조건: (PR-AUC, 파라미터 수, MMAC, ONNX 크기) 4열 표 + 선택 근거 1문장.
    선택된 D 만 5 fold × 3 seed 로 확정 재실행. **탐색 숫자는 확정 값으로 인용하지 않는다**
  - 💡 **서사 고려**: 성능이 같다면 **작은 D 가 논문에 유리하다** — "16차원 벡터만으로
    된다"가 더 인상적이고 모델 크기·메모리에도 유리하다. 성능이 뚜렷이 오르면 키운다.
    **결과를 보고 정하되, 이 선호를 미리 적어둔다**

- [ ] **T3-8. 🔴 비대칭 stride 절제 실험 (sym16 대조군)** — **P0 신설 (2026-08-05)**
  - **왜 신설했나**: `encoder.py` 는 *"비대칭 stride 가 이 설계의 핵심이다"* 라고 적고 있고,
    이것이 논문 Method 에서 **가장 독자적인 설계 주장**이다. 그런데 근거가
    **계산 논거뿐이다** — "세로 stride 16 이면 눈꺼풀 8.73 px 이 0.55 px 가 되어 사라진다".
    **`grep -rl "sym16" results/` 결과 0건 — 한 번도 학습해 본 적이 없다.**
  - 심사자가 반드시 묻는다: *"대칭 stride 를 실제로 돌려봤나?"*
  - 비용: **거의 없다.** `SPECS["sym16"]` 이 이미 구현돼 있고 `build(arch, D)` 가
    arch 를 인자로 받는다. `--arch sym16` 한 줄이면 된다
  - 스윕: `sym16` vs `vpres` (여유 되면 `vfull`), fold 0·1 × 3 seed = 6런
  - 완료 조건: 세 구조의 (PR-AUC, conv MMAC, 병목에 남는 눈꺼풀 px) 3열 표.
    **sym16 이 뚜렷이 낮아야 vpres 의 34% 추가 연산이 정당화된다**
  - 참고 수치 (`E.report()` 실측):

    | 구조 | 특징맵 | 세로 stride | 병목 신호 | conv MMAC |
    |---|---|---:|---:|---:|
    | sym16 | 128×4×10 | 16 | **0.55 px** | 9.22 |
    | **vpres** (채택) | 64×32×5 | 2 | **4.37 px** | **12.41** |
    | vfull | 64×64×5 | 1 | 8.73 px | 24.21 |

  - ⚠️ **만약 sym16 이 비슷하게 나오면** vpres 를 쓸 이유가 약해진다. 그때는
    9.22 MMAC 짜리 sym16 이 오히려 edge 에 유리하므로 **설계 주장을 바꿔야 한다.**
    결과를 보기 전에 이 가능성을 적어둔다

  - **PSNR 숫자 하나는 의미 없다.** 눈 크롭은 저분산 그레이라 정보 0 에서도 PSNR 이 높다

### 9-1. Q4 해소 — image_cnn 의 "파라미터 예산" 이란

**문제**: `ours` 는 크롭 → encoder → **D차원 병목** → 헤드 구조라 표현이 좁다.
`image_cnn` 은 병목 없이 크롭에서 바로 판정하므로 **파라미터가 훨씬 많아질 수 있다.**
이 상태로 image_cnn 이 이기면 *"임베딩이 나빠서"* 인지 *"모델이 커서"* 인지 구분되지 않는다.

**결정 — 두 변형을 모두 낸다.**

| 변형 | 정의 | 답하는 질문 |
|---|---|---|
| **image_cnn-free** | 크기 제한 없이 합리적으로 설계한 이미지 기반 CNN | *"성능 천장은 어디인가"* |
| **image_cnn-matched** | 총 파라미터 수(또는 MMAC)를 `ours` 와 **±10% 이내로 맞춘** 변형 | *"같은 비용이면 임베딩 경로가 유리한가"* |

두 줄을 Table I·II 에 모두 넣고, 파라미터 수와 MMAC 을 같은 표에 병기한다.
어느 쪽이 나와도 해석이 가능해진다. 완료 조건: T3-1 산출물에 두 변형 모두 포함.

### 9-2. Q5 해소 — Pi 5 측정 해상도

문헌 조사 결과, **640×480 @ 30 fps 가 이 분야의 사실상 표준**이다.

| 근거 | 값 |
|---|---|
| Raspberry Pi 5 기반 졸음 검출 데이터셋 (2025) | **640×480, 30 fps**, H.264 |
| PiCamera 기반 EAR 깜빡임 검출 구현들 | **640×480**, 최대 32 fps |
| Eyeblink8 (우리 v1 클립) | **640×480**, 408 blinks / 70,992 frames |
| 일부 데이터셋 (정면·안경·상방 시선 4클립) | 320×240, 30 fps |
| mEBAL2 (우리 v2 학습 데이터) | 1280×720 |

**결정**

- **주 측정: 640×480 @ 30 fps.** 논문 Table II 의 기준값. 선행 연구와 직접 비교 가능하고
  v1 측정(`results/pi_ours.json`)과도 같은 조건이라 인코더 변경의 효과만 분리된다.
- **보조 측정: 1280×720.** mEBAL2 원본 해상도. "학습 데이터와 같은 해상도에서도 도는가"에 답한다.
- 두 해상도 모두 ours / ear / image_cnn 3자를 잰다 (총 6런 × 5분).
- ⚠️ **해상도가 바뀌면 얼굴 검출 비용이 지배적으로 바뀐다.** v1 에서 detect 가 e2e 의
  약 67% (7.76 / 11.53 ms p50) 였다. 720p 에서는 이 비중이 더 커진다 —
  **encoder 비용 차이가 묻히지 않도록 단계별 분해를 반드시 함께 보고한다.**

> 출처: [Raspberry Pi 5 졸음 검출 데이터셋 (PMC)](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12630088/) ·
> [PyImageSearch Pi facial landmarks + drowsiness](https://pyimagesearch.com/2017/10/23/raspberry-pi-facial-landmarks-drowsiness-detection-with-opencv-and-dlib/) ·
> [Embedded System for Eye Blink Detection (IEEE)](https://ieeexplore.ieee.org/document/9509908/)
> — 전부 [검색요약] 이다. **논문 인용 전 원문 확인 필요** (T6-1).
